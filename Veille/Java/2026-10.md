# Veille Java — Octobre 2026

*Publié le 1er novembre 2026*

---

## 🔥 Les 3 faits marquants

1. **La compromission d'eMudhra a mis Java en première ligne.** Huit clés privées d'autorités intermédiaires compromises : un attaquant pouvait usurper n'importe quel site. Problème spécifiquement Java : **la JVM ne vérifie pas la révocation par défaut**, donc même un runtime patché en 27.0.1.0.2 accepte les certificats frauduleux tant qu'on n'agit pas sur le keystore. Azul a sorti un patch hors cycle le 21 octobre, un jour après le CPU d'Oracle.
2. **JDK 28 est désormais complet côté fonctionnalités (10 JEPs).** Valhalla en preview (JEP 401 + 539), API JSON standard en incubateur (JEP 540), compilation AOT native (JEP 544), ZGC adaptatif (545, 546), Structured Concurrency finalisé. GA annoncée le **9 mars 2027** — la release la plus structurante depuis Java 8.
3. **Le train de releases de Spring a tenu sa promesse.** Premier vrai « Patch Thursday » le 22 octobre, puis 17 projets en RC1 en 48 h : Boot 4.2.0-RC1, Framework 7.1.0-RC1, Cloud 2026.0.0-RC1 « Paddington », Spring AI 2.1.0-RC1. Le rythme mensuel d'un seul jour est maintenant une réalité mécanisable côté CI.

### 🚨 eMudhra : l'action à faire ce mois-ci (pas le mois prochain)

Le 19 octobre, la compromission des clés privées de **huit certificats intermédiaires eMudhra** a été divulguée aux *trust stores*. Les certificats ont été bloqués dans Firefox et Chrome dès le 17, côté Microsoft le 20, côté Apple le 22. Oracle a publié l'alerte [CVE-2026-91403](https://www.oracle.com/security-alerts/alert-cve-2026-91403.html).

Pourquoi c'est plus grave en Java qu'ailleurs, de l'aveu d'Azul :

> *« Java makes this worse than it sounds: it does not check certificate revocation by default. Until the certificates are blocked in the JDK itself, a Java application accepts a fraudulent certificate issued with those keys as valid. »*

La procédure officielle est sur [openjdk.org/emudhra](https://openjdk.org/emudhra) — et **elle s'applique même si vous êtes déjà en 27.0.1.0.2, 25.0.5.0.2, 21.0.13.0.2, 17.0.21.0.2, 11.0.33.0.2 ou 8u511 b32**.

```bash
# 1) Vérifier si le runtime est exposé (fonctionne depuis JDK 8)
java CheckCerts.java        # https://cr.openjdk.org/~mr/CheckCerts.java

# 2) Retirer les deux racines concernées du keystore (JDK 11+)
keytool -delete -cacerts -alias "emsigneccrootcag3 [jdk]"
keytool -delete -cacerts -alias "comodoaaaca [jdk]"

#    ...ou activer la vérification de révocation (impact perf/latence réseau)
java -Dcom.sun.net.ssl.checkRevocation=true \
     -Dcom.sun.security.enableCRLDP=true -jar app.jar

# 3) Vérifier les JAR signés (JDK 17+)
jarsigner -verify -revcheck -strict mon-app.jar
```

⚠️ **Piège Debian/Ubuntu** : les paquets OpenJDK sont censés utiliser les certificats système via `ca-certificates-java`, mais un [bug de longue date](https://bugs.debian.org/cgi-bin/bugreport.cgi?bug=1069251) fait que mettre à jour les deux paquets ne suffit pas. Le contournement, en root :

```bash
rm -f /etc/ssl/certs/java/cacerts
update-ca-certificates --fresh
```

**JEP 401 — la première preview de Valhalla.** Un `value` object est immuable et **sans identité** : `==` compare les champs au lieu des références. 30 classes du JDK deviennent des value classes : les huit wrappers primitifs, `Number`, `Record`, les quatre `Optional*`, les types `java.time.*` et les dates des chronologies non-ISO.

```java
// jshell --enable-preview (JDK 28)
value record Point(int x, int y) {}

Point p = new Point(17, 3);
Objects.hasIdentity(p);          // false
new Point(17, 3) == p;           // true  (en JDK 27 : false)

Integer x = 1996, y = 1996;
x == y;                          // true  — y compris hors cache -128..127

LocalDate d1 = LocalDate.of(1996, 1, 23);
LocalDate d3 = d1.plusYears(30).minusYears(30);
d1 == d3;                        // true
```

Un `value class` peut aussi encapsuler un stockage compact, ce qu'un record ne sait pas faire :

```java
value class EURCurrency {
    private long cs;                     // centimes, implicitement final

    public EURCurrency(long e, int c) { this(e, c, false); }
    private EURCurrency(long cs) { this.cs = cs; }
    public EURCurrency(long e, int c, boolean neg) {
        this(neg ? -e * 100 - c : e * 100 + c);
    }
    public long euros() { return Math.abs(cs) / 100; }
    public int cents()  { return (int) Math.abs(cs) % 100; }
}
```

> ⚠️ **Le vrai risque n'est pas d'écrire `value`, c'est de ne rien écrire.** Les 30 classes basculent *même pour du code compilé en Java 17* dès que la preview est active. Conséquences : `==` peut renvoyer `true` là où il renvoyait `false` ; plus de moniteur (donc `synchronized`, `wait`/`notify` → erreur de compilation ou `IdentityException`) ; `java.lang.ref` et `WeakHashMap` inutilisables ; `setAccessible` sur un champ → `IllegalAccessException`. Le [heads-up Qualité du 27 octobre](https://inside.java/2026/10/27/quality-heads-up/) recommande de tester la CI **avec et sans** `--enable-preview`.
>
> Second piège : avec la preview active, les constructeurs de records s'exécutent en **early construction** (suite de JEP 513) — un constructeur compact qui appelle une méthode d'instance ne compile plus. Refactorisation obligatoire vers la forme non compacte.

**JEP 540 — enfin du JSON dans le JDK.** API minimaliste, stricte RFC 8259, sans mode permissif ni data binding. Le module `jdk.incubator.json` s'active explicitement.

```java
// java --add-modules jdk.incubator.json Weather.java
import jdk.incubator.json.Json;
import jdk.incubator.json.JsonValue;

var json = Json.parse(response.body());
json.get("properties").get("periods").asList().stream()
    .mapToInt(j -> j.get("temperature").asInt())
    .average()
    .ifPresent(IO::println);

// Génération
IO.println(JsonObject.of(Map.of("providers",
        JsonArray.of(List.of(JsonString.of("SUN"), JsonString.of("SunEC"))))));
// {"providers":["SUN","SunEC"]}
```

`JsonValue` est une interface **sealed** à six sous-types (`JsonString`, `JsonNumber`, `JsonBoolean`, `JsonNull`, `JsonObject`, `JsonArray`) : un `switch` exhaustif sans `default` est possible. Les JEPs 128 puis 198 attendaient ça depuis 2018. Usage cible : scripts, parsing exploratoire, configuration interne au JDK — **pas** un remplaçant de Jackson.

**JEP 544 — le dernier étage de Leyden.** Le cache AOT stocke désormais du **code natif optimisé** produit pendant un *training run*, chargé instantanément au démarrage. Aucune modification de code applicative.

```bash
# Training run : produit le cache avec bytecode pré-lié, profils ET code natif
java -XX:AOTCacheOutput=app.aot -cp app.jar com.example.App

# Production : chargement du code AOT
java -XX:AOTCache=app.aot -cp app.jar com.example.App

# Refuser de démarrer si le cache est incompatible (utile en CI/CD)
java -XX:AOTMode=required -XX:AOTCache=app.aot -cp app.jar com.example.App
```

L'intérêt face à GraalVM Native Image : le code AOT et le code JIT **cohabitent** (mêmes compilateurs C1/C2), donc un changement de charge de travail déclenche de la déoptimisation/réoptimisation classique. On garde l'agilité du JIT. Contrepartie : cache plus gros, et un seul jeu d'optimisations par cache.

**JEP 545/546 — ZGC devient autonome.** 545 accélère l'acquisition de mémoire physique au démarrage ; 546 ajuste la taille du heap **tout seul**, en fonction de la charge et de la pression des applications voisines. Objectif affiché : la performance d'un heap réglé à la main, sans le régler. Combiné à JEP 544, ça dessine une JVM où « démarrage rapide, pas de warmup, pas de `-Xmx` » devient une configuration par défaut crédible.

**Détail de serviceability** : [JDK 27 G1/Parallel/Serial GC changes](https://tschatzl.github.io/2026/08/10/jdk27-g1-serial-parallel-gc-changes.html) (30 oct.) documente ce que change concrètement JEP 523 — G1 par défaut partout — pour ceux qui comptaient sur Serial dans des conteneurs serrés.

**Spring AI 2.1 : les deux ajouts qui changent un design.**

*Session memory* — un log append-only d'événements avec compaction sur frontière de tour. Plus de `ChatMemory` en fenêtre glissante qui coupe un appel d'outil de son résultat ; et les advisors sont **sans état**, donc n'importe quelle instance peut jouer n'importe quel tour.

```java
@Bean
ChatClient chatClient(ChatModel chatModel, SessionService sessionService) {
    return ChatClient.builder(chatModel)
        .defaultAdvisors(SessionAdvisors.builder(sessionService)
            .compaction(new TurnCountTrigger(20),
                        WindowCompactionStrategy.builder().lastTurns(10).build())
            .build())
        .build();
}

String answer = chatClient.prompt().user("Bonjour !")
    .advisors(SessionAdvisors.session("session-abc"))
    .call().content();
```

> `ChatMemory`, `MessageWindowChatMemory`, `ChatMemoryRepository`, `MessageChatMemoryAdvisor` et les repos JDBC/Cassandra/Neo4j/MongoDB/Redis sont **dépréciés pour suppression en 3.0.0**. Migration à planifier dès maintenant.

*Tool call confirmation* — le pattern « l'humain valide l'action irréversible », enfin dans le framework :

```java
class BookingTools {
    @Tool(description = "Book a flight", requiresConfirmation = true)
    String bookFlight(String flightNumber) { return bookingService.book(flightNumber); }
}
```

La boucle d'appel s'arrête avant d'exécuter ; l'application rend un `ToolCallDecision` par appel (allow / deny + message), puis reprend via `ToolCallingManager.executeToolCalls(...)`. **Aucun état conservé pendant la pause** → ça survit à un redémarrage, contrairement à un `ThreadLocal` ou une session en mémoire.

## 5. 🔮 Analyse et perspectives

### ✅ Impactant — à faire ce mois-ci

1. **Traiter eMudhra sur tous vos runtimes, y compris ceux à jour.** C'est le seul point de ce bulletin qui relève de l'incident, pas de la veille. `CheckCerts.java` d'abord, puis suppression des deux racines du keystore (ou activation de `checkRevocation`). Pensez aux images Docker : le `cacerts` est dans l'image, un `docker pull` d'une image rebuildée suffit, un rebuild à partir d'un cache non.
2. **Planifier JDK 28 dans vos tests, pas dans votre prod.** 401 et 539 arrivent en preview mais changent le comportement des wrappers et de `java.time` **sans recompilation**. Ajouter une matrice CI `JDK 28` (preview off) et `JDK 28 --enable-preview` coûte une ligne de YAML et évite une surprise en mars 2027.
3. **Mécaniser le Patch Thursday.** Une date par mois (jeudi après le 3ᵉ lundi), un ticket récurrent, un build, un déploiement. Ce mois-ci la preuve est faite : 4.1.2 avec 126 correctifs est sorti en un seul bloc.
4. **Migrer Spring AI 2.0 → 2.1 avant la GA de 2.1.** `ChatMemory` est déprécié pour suppression en 3.0.0. Le remplacement (session memory) n'est pas un renommage : c'est un autre modèle (log d'événements, compaction sur frontière de tour, advisors sans état). Le faire maintenant, c'est une itération ; le faire en 3.0, c'est un chantier.
5. **Vérifier le statut de support de vos streams Quarkus.** 3.27 est hors support depuis le 24 septembre, malgré un patch d'urgence le 19 octobre. LTS 3.40 → support jusqu'au 30 septembre 2027 ; c'est la cible avant Quarkus 4.

### ⚪ Anecdotique — pas d'urgence

- Release d'urgence de Apache POI 6.0.0 : le passage à **JDK 17 minimum** est le seul vrai impact (et il concerne surtout des outils bureautiques internes).
- Les 3.2.x de Micronaut : correctifs de sécurité appliqués, aucune nouveauté d'API à étudier.
- TornadoVM 7.1/7.2, Gatherers4j 0.15, JobRunr 9.0.2, GlassFish 8.0.5 : utiles si vous êtes déjà sur ces briques, sans effet de bord ailleurs.
- Azul Payara 7.5.0 et le passage du support de JDK 27 dans Open Liberty : bonne nouvelle pour la filière Jakarta EE, zéro impact sur une stack Spring.

### 👀 À surveiller

- **JDK 28, le vrai « storm » (9 mars 2027).** Quatre JEPs de fond en une seule release : Valhalla (401+539), JSON standard (540), AOT natif (544), ZGC autonome (545+546), plus Structured Concurrency finalisé. Le pattern qui se dessine : Java répond à la contrainte cloud (démarrage, mémoire, densité) par le *runtime*, pendant que les autres langages répondent par la compilation statique. À lire dès maintenant : le JEP 401 en entier, et le heads-up Qualité sur les 30 classes qui changent de sémantique.
- **Le tournant « IA trouve les CVE ».** 28 CVE sur 38 chez Camel découvertes par Claude, 80 rapports/mois chez Spring, un CSPU créé de toutes pièces pour le JDK. La question ouverte n'est plus « faut-il patcher plus vite » mais « qui absorbe le volume » : les projets qui n'ont pas d'équipe sécurité dédiée vont devoir choisir entre cadence et couverture.
- **Le Rampdown de JDK 28 (3 décembre 2026).** C'est la date limite pour faire remonter un problème de compatibilité sur JEP 401/539. Après, il faudra attendre 29.
- **Quarkus 4** (beta attendue, GA annoncée pour novembre) : Vert.x 5 + Netty 4.2 + Jackson 3 + abandon de Java 17. La fenêtre raisonnable reste d'atterrir sur 3.40 LTS avant, pas pendant.
- **Jakarta EE 12 Core Profile (1ᵉʳ décembre).** Premier jalon réel de la plateforme, et test de crédibilité du nouveau calendrier en trois vagues.
