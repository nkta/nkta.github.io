# Veille Java — Septembre 2026

*Publié le 1er octobre 2026*

---

## 🔥 Les 3 faits marquants

1. **JDK 27 est sorti le 15 septembre** — post-quantique activé par défaut en TLS, *Compact Object Headers* par défaut (‑10 à ‑20 % de heap), G1 partout. La release la plus « gratuitement rentable » depuis longtemps : on gagne de la perf sans changer une ligne de code.
2. **Spring réinvente son cycle de release** — le train passe de deux semaines à **une seule journée par mois** (« Patch Thursday », le jeudi après le 3ᵉ lundi). Motif assumé : ~80 rapports de sécurité communautaires par mois et plus de 160 CVE corrigées depuis mars.
3. **Quarkus 3.40 LTS (+ ~28 CVE en urgence)** — nouvelle LTS le 30 septembre, mais aussi un correctif d'urgence le 22 septembre sur les LTS 3.27 et 3.33 : Netty, zstd-jni et Hibernate ORM étaient touchés.

## 1. ☕ JDK : Java 27 en production, Valhalla se prépare pour 28

### JDK 27 — GA le 15 septembre 2026, 9 JEPs

| JEP | Titre | Statut |
|-----|-------|--------|
| [523](https://openjdk.org/jeps/523) | Make G1 the Default Garbage Collector in All Environments | ✅ Final |
| [534](https://openjdk.org/jeps/534) | Compact Object Headers by Default | ✅ Final |
| [536](https://openjdk.org/jeps/536) | JFR In-Process Data Redaction | ✅ Final |
| [527](https://openjdk.org/jeps/527) | Post-Quantum Hybrid Key Exchange for TLS 1.3 | ✅ Final |
| [531](https://openjdk.org/jeps/531) | Lazy Constants (3ᵉ preview) | 👀 Preview |
| [532](https://openjdk.org/jeps/532) | Primitive Types in Patterns, `instanceof` et `switch` (5ᵉ preview) | 👀 Preview |
| [533](https://openjdk.org/jeps/533) | Structured Concurrency (7ᵉ preview) | 👀 Preview |
| [538](https://openjdk.org/jeps/538) | PEM Encodings of Cryptographic Objects (3ᵉ preview) | 👀 Preview |
| [537](https://openjdk.org/jeps/537) | Vector API (12ᵉ incubator) | ⚪ Incubator |

JDK 27 est une release **non-LTS** (6 mois de support Premier, remplacée par JDK 28 en mars 2027). Environ 2 500 correctifs, dont ~2 390 dans OpenJDK et 155 dans JavaFX.

**JEP 534 — Compact Object Headers par défaut.** L'en-tête objet passe de 96 à 64 bits sur les architectures 64 bits (Mark Word et Class Word fusionnés). C'était expérimental en JDK 24, activable en JDK 25 via `-XX:+UseCompactObjectHeaders` ; en JDK 27 c'est le comportement par défaut. Gain annoncé : **‑10 à ‑20 % de heap** et **+5 à +10 % de débit** sur les applications à nombreuses petites allocations. Le JVM réserve déjà 4 bits dans l'en-tête pour les futurs *value classes* de Valhalla.

**JEP 523 — G1 partout.** Le JVM ne bascule plus vers le collecteur Serial dans les environnements « client-class » (petits conteneurs, machines peu dotées, JVM avec peu de CPU). Quand rien n'est spécifié sur la ligne de commande, c'est **toujours G1**. Attention aux déploiements serrés en mémoire/CPU : c'est le changement le plus susceptible de faire bouger vos courbes.

**JEP 527 — Post-quantique hybride TLS 1.3.** C'est quasi transparent : les applications qui utilisent `javax.net.ssl` bénéficient des algorithmes hybrides (RFC 9954) **sans modification de code**. C'est la brique PQC la plus « adoptable » immédiatement, avant la généralisation des signatures quantiques (JEP 497) et de la KDF (JEP 510).

**JEP 536 — JFR redacte par défaut.** Les arguments de ligne de commande, les valeurs initiales des variables d'environnement et des propriétés système sont masqués **avant de quitter le processus**. Une valeur contenant `token`, `password` ou `secret` (ex. `ACCESS_TOKEN`, `javax.net.ssl.keyStorePassword`) est automatiquement remplacée. Fini les fuites de secrets par les fichiers de diagnostic.

> ⚠️ **Changements à vérifier avant migration JDK 27** : `-XX:UseCompressedClassPointers` est **obsolète** (warning au démarrage), la JVMCI est **supprimée**, `-XX:InitiatingHeapOccupancyPercent` devient `-XX:G1IHOP`, et les options `-noclassgc`, `-noverify`, `-verifyremote`, `-Xverify:none` disparaissent.

```java
// JEP 531 — Lazy Constants (3e preview, --enable-preview)
// Un objet non modifiable, dont le JVM peut se servir comme d'un champ final
// (constant folding) sans payer l'initialisation au chargement de la classe.

public final class PricingService {
    // Initialisé au premier accès seulement, jamais recalculé, JIT-friendly
    private static final LazyConstant<PriceGrid> GRID =
            LazyConstant.of(PricingService::loadGridFromDatabase);

    public BigDecimal priceFor(String sku) {
        return GRID.get().lookup(sku);   // pas de double-checked locking maison
    }
}
```

Changements d'API dans cette 3ᵉ preview : suppression de `isInitialized()` et `orElse()` (dont l'usage cassait le modèle d'initialisation) et ajout de `Set.ofLazy(...)` à côté des fabriques `lazyList` / `lazyMap`.

```java
// JEP 533 — Structured Concurrency (7e preview)
try (var scope = StructuredTaskScope.open(Joiner.<Detail>allSuccessfulOrThrow())) {
    var user  = scope.fork(() -> fetchUser(userId));    // thread virtuel
    var order = scope.fork(() -> fetchOrder(orderId));
    scope.join();                                        // échec/annulation propagés ensemble
    return new Page(user.get(), order.get());
}
```

### Performances : ce que le JVM a gagné (Inside.java)

Au-delà des deux changements « globaux », l'équipe HotSpot a publié [le détail des gains de JDK 27](https://inside.java/2026/09/28/performance-update-jdk27/), mesurés en JMH :

| Optimisation | Gain mesuré |
|--------------|-------------|
| `HashMap.putAll()` / `new HashMap<>(map)` spécialisés | 61 % à **86 %** (map non modifiable de 150 entrées : 10 593 → 1 533 ns/op) |
| `URL.toString()` / `URLStreamHandler.toExternalForm()` | ≥ 60 % (chemin chaud en startup et chargement de classes) |
| `AttributedString` (texte stylé, Swing) | 35–40 % d'itération, ~20 % d'allocation en moins |
| Ouverture de fichier Unix (`FileOutputStream`, `RandomAccessFile`) | 14 % (suppression d'un `fstat` redondant) |

Ces chiffres sont **locaux**, pas ceux d'une application complète. Le conseil de l'équipe est bon à prendre : mesurer d'abord, puis n'activer/désactiver qu'**une variable à la fois** (`-XX:-UseCompactObjectHeaders`, le choix du GC) pour expliquer les écarts, sur des indicateurs incluant temps de démarrage, taux d'allocation, *live set* et latence de queue — pas seulement le débit de pointe.

### JDK 28 (mars 2027) — Valhalla arrive pour de vrai

Le mois a été marqué par l'arrivée des JEPs Valhalla dans la cible de JDK 28 :

- **[JEP 401 — Value Classes and Objects (Preview)](https://openjdk.org/jeps/401)** : des objets sans identité, uniquement définis par la valeur de leurs champs (`final`), que le JVM peut aplatir en mémoire. Le keyword `value`, l'égalité `==` qui change de sémantique, et la migration de classes existantes comme `Integer`. Après 12 ans de projet, c'est la nouveauté la plus structurante pour la décennie à venir.
- **[JEP 539 — Strict Field Initialization in the JVM (Preview)](https://openjdk.org/jeps/539)** : le mécanisme de vérification bytecode qui impose qu'un champ soit initialisé avant lecture (plus jamais de `0` ou `null` par défaut observé).
- **[JEP 541 — Deprecate the macOS/x64 Port for Removal](https://openjdk.org/jeps/541)** : ciblé le 29 septembre, entretien arrêté au JDK 27.

Également en préparation pour 28 : **JEP 544 Ahead-of-Time Code Compilation** (passé *Proposed to Target* — du code natif optimisé disponible dès le démarrage de HotSpot), **JEP 543 Structured Concurrency** (passé *Candidate* pour une finalisation sans changement après 7 previews), et deux JEPs ZGC encore à l'état *Candidate* ([545](https://openjdk.org/jeps/545) *Faster Startup and Warmup*, [546](https://openjdk.org/jeps/546) *Adaptive Heap Sizing*).

### Java Verified Portfolio : Helidon 27, JavaFX 27

Oracle a aligné son portefeuille vérifié sur la numérotation OpenJDK : **Helidon 27**, **JavaFX 27**, Jipher 20 et une extension JVP pour VS Code. Helidon 27 est le premier projet à appliquer le [modèle « Tip & Tail » (JEP 14)](https://openjdk.org/jeps/14) : Helidon 27 = le *Tip* (versionné comme le JDK), Helidon 4.5.5 = le *Tail* (versionné en semver, pour les équipes qui veulent une base de production plus longue). JavaFX 27 apporte notamment un pipeline de rendu *metal* sur macOS.

## 2. 🏗️ Frameworks

### Spring — le train de release devient un « Patch Thursday »

C'est la nouvelle **organisationnelle** du mois, et elle compte plus que n'importe quelle release individuelle. [Michael Minella l'annonce le 21 septembre](https://spring.io/blog/2026/09/21/releasing-spring-for-modern-challenges) :

- Le train de release passe d'**étalé sur deux semaines à une seule journée** : le **jeudi suivant le 3ᵉ lundi du mois**, jour historiquement utilisé pour Spring Boot. Tout le portefeuille (Boot, Framework, Data, Security, Integration, Batch, Cloud…) sort ensemble, avec ses correctifs CVE.
- **Prochaine échéance : jeudi 22 octobre 2026.**
- Le **mois de septembre était volontairement « milestones only »** (24 septembre) : aucune release de patch.

La raison est explicite et vaut d'être retenue : depuis mars, l'équipe encaisse **~80 nouveaux rapports de sécurité communautaires par mois** (en plus de son propre scan par modèles), et **plus de 160 nouvelles CVE** ont été corrigées. Le constat : dans un monde où une CVE est exploitée en quelques heures, un train étalé sur deux semaines signifie « des correctifs de sécurité qui sortent au compte-gouttes sur 14 jours ».

**Impact concret pour une équipe :** une seule fenêtre de mise à jour par mois au lieu d'une gymnastique sur deux semaines. C'est plus simple à planifier — et ça rend l'inaction mensuelle plus difficile à justifier.

### Quarkus — la LTS 3.40, et 28 CVE corrigées en urgence

| Release | Date | Détail |
|---------|------|--------|
| **Quarkus 3.40 LTS** | **30 sept.** | Nouvelle LTS (support 12 mois), basée sur la 3.39 |
| Quarkus 3.39.5 | 24 sept. | Maintenance |
| Quarkus 3.39.4 | 17 sept. | Maintenance |

```bash
# Mettre à jour vers la nouvelle LTS (gère aussi les renommages JUnit 6 / Testcontainers 2)
quarkus update --stream=3.40
```

Quarkus 3.40 LTS est une **continuation directe de 3.39** : le guide de migration 3.40 est vide, et venir de 3.39 ne demande rien. Depuis la LTS précédente (3.33), en revanche, il y a du contenu : Quarkus Signals (3.36), modularité par extension et sérialiseurs Jackson sans réflexion (3.37), Hibernate ORM 7.4, éviction pondérée du cache Caffeine L2 (3.38), et la **cryptographie post-quantique dans le TLS registry** (3.39) — le même mouvement que JDK 27, mais côté configuration Quarkus. Côté plateforme : Camel Quarkus 3.40.0, Quarkus CXF 3.40.0, Quarkus MCP Server 2.0.1, LangChain4j 1.13.3, JobRunr 9 avec support J-0. La communauté passe à **1 250 contributeurs**.

**⚠️ Le fait du mois, c'est la vague de sécurité du 22 septembre.** Les LTS 3.27 et 3.33 ont reçu des patchs d'urgence couvrant ~28 CVE, dont plusieurs sévères :

- **CVE-2026-77874 — Hibernate ORM** : injection SQL via un segment de chemin JSON non échappé (exfiltration de données, contournement d'autorisation). La plus grave du lot.
- **CVE-2026-87743 — Quarkus Vert.x HTTP** : contournement d'autorisation par divergence de normalisation de chemin dans la sécurité HTTP. À corriger en priorité si vous avez des URL filtrées.
- **CVE-2026-81829 — SmallRye JWT** : SSRF non authentifié via l'en-tête `kid` dans `AwsAlbKeyResolver`.
- **CVE-2026-87742 — WebSockets Next** : OOM par mise en tampon non bornée.
- **5 CVE Netty de *request smuggling*** (Transfer-Encoding, chunk-size, CONNECT HTTP/1 → HTTP/2, HPACK) — de la famille de celles qui se corrigent en urgence côté infrastructure.
- **9 CVE zstd-jni** (use-after-free, out-of-bounds read) + FreeMarker path traversal + memory leak dans SmallRye Fault Tolerance.

À noter : la page [quarkus.io/releases](https://quarkus.io/releases/) affiche encore 3.33 comme « LTS recommandée » et 3.40 en « Upcoming » — la doc a un train de retard sur l'annonce du 30 septembre.

**Et après ?** Quarkus 4.0 : Beta 1 imminente, **GA en novembre 2026**. Le chantier est lourd — remplacement du cœur I/O (Vert.x 5.1.2 + Netty 4.2), **Jackson 3**, et abandon du support Java 17. La stratégie raisonnable : **atterrir sur 3.40 LTS maintenant** (supportée jusqu'en septembre 2027), stabiliser, et planifier la migration 4.0 au premier trimestre 2027 quand l'écosystème d'extensions aura suivi.

### Bonnes pratiques retenues du mois

- **Tester les nouveaux défauts séparément.** Le conseil de l'équipe JDK vaut d'être érigé en règle : un changement de défaut (GC, layout d'objet) se mesure avec un protocole A/B, une variable à la fois, sinon vous attribuerez à tort une régression à la migration.
- **Les CVE ne se traitent plus par lots trimestriels.** Spring l'a acté en réorganisant tout son train de release ; Quarkus a sorti des patchs d'urgence en pleine semaine. La pratique qui monte : une **fenêtre mensuelle fixe** de mise à jour, plus un canal d'urgence pour les CVE critiques.
- **JFR redacte par défaut : vérifiez vos pipelines d'observabilité.** Un diagnostic JFR ingéré quelque part contient désormais moins de données qu'avant — c'est voulu, mais cela peut casser des tests qui s'appuient sur les propriétés système enregistrées.

## 5. 🔮 Analyse et perspectives

### ✅ Impactant — à faire rapidement

1. **Migrer sur JDK 27 (ou 25 LTS) et mesurer.** C'est une des rares releases où le gain arrive sans travail : heap ‑10 à ‑20 %, débit +5 à +10 %, PQC TLS par défaut. Sur JDK 25 LTS le gain est déjà là pour les *compact object headers* (à activer), donc si vous êtes en LTS, activez-les en attendant 29.
2. **Traiter la vague Netty/zstd-jni/Hibernate de la fin septembre.** Si vous êtes sur Quarkus (3.27 LTS, 3.33 LTS, 3.39.x) ou sur une stack Netty directe, c'est du patch de sécurité, pas de la maintenance. `zstd-jni` en particulier arrive en dépendance transitive dans beaucoup de chaînes.
3. **Adopter la fenêtre mensuelle de mise à jour Spring.** Une seule date par mois (jeudi après le 3ᵉ lundi) rend la veille CVE mécanisable : un ticket récurrent, un test de non-régression, un déploiement.
4. **Réévaluer les paramètres GC si vous tournez sur des petits conteneurs.** G1 devient le GC de tous les environnements en JDK 27 ; là où le Serial ou un `-XX:ActiveProcessorCount` ajusté était le choix implicite, il faut désormais l'écrire explicitement.

### ⚪ Anecdotique — pas d'urgence

- Les 6 milestones Spring de septembre : à vocation de préparation de novembre, aucun correctif de sécurité.
- Quarkus 3.39.2 → 3.39.5 : maintenance de routine.
- TornadoVM 6.1 → 7.0 dans le même mois, Groovy 6.0, Maven 4.0-RC7, Gradle 9.8-RC1 : intéressants pour qui suit le langage/GPU, sans impact direct sur un projet web classique.
- Helidon 27 / JavaFX 27 : ils comptent surtout pour la stratégie JVP d'Oracle et le modèle Tip & Tail.

### 👀 À surveiller

- **JDK 28 et Valhalla (mars 2027).** JEP 401 + JEP 539 sont dans la cible. C'est la première preview publique des *value classes* après douze ans — commencez à lire le JEP maintenant, vous serez en avance d'une release. Combiné à JEP 544 (compilation AOT native au démarrage de HotSpot), JDK 28 pourrait être plus structurant que sa version de numéro ne le suggère.
- **Quarkus 4.0 (novembre 2026).** Vert.x 5 + Netty 4.2 + Jackson 3 + fin de Java 17. Migration nettement plus lourde que 3.33 → 3.40 : c'est *maintenant* qu'il faut atterrir sur 3.40 LTS pour ne pas subir deux migrations en même temps.
- **Le virage sécurité de l'écosystème.** ~80 rapports/mois chez Spring, ~28 CVE en un release d'urgence chez Quarkus, « les rapports par modèles de frontière » cités comme source : les CVE vont continuer à sortir plus vite, portées par l'IA offensive **et** défensive. Les pratiques qui survivent sont celles qui intègrent ce débit par défaut, pas celles qui résistent.
- **Les modèles de décision typés (Jev/TypeSafe) greffés dans Spring AI.** Passer d'un LLM qui rend de la prose à parser à un modèle qui rend une décision typée avec un score est un changement de design, pas juste d'API. À suivre pour tout backend qui met de l'IA dans une chaîne de décision.
- **Jakarta EE 12 : Core Profile en décembre 2026.** Premier jalon réel de la plateforme depuis le retard de l'EE 11 — à confirmer ou infirmer fin décembre.
