# Veille DevOps – Août 2026

## Synthèse du mois

Août 2026 restera comme un mois de **consolidation et de nettoyage** dans l'écosystème DevOps. Le fait marquant est la sortie de **Kubernetes v1.37 « Garhwal »** le 26 août : 67 améliorations (16 stables, 23 bêta, 27 alpha, 1 dépréciation) qui tranchent enfin avec l'historique de la plateforme — la **Metrics API devient GA après neuf ans de bêta**, les **pod-level resources**, **Pod Certificates** et **ClusterTrustBundles** passent en stable, tandis que le projet assume une dépréciation explicite de `kube-proxy ipvs` et des **cgroup v1**. Le message est clair : Kubernetes priorise la maturité de production, quitte à retirer l'héritage. C'est aussi le reflet d'une plateforme devenue de facto le socle de l'IA (66 % des organisations hébergeant des modèles génératifs s'appuient sur Kubernetes).

Le second axe du mois est **l'agentification massive de la chaîne DevOps**. GitLab généralise son **Duo CLI** et ses **custom flows** (workflows YAML orchestrant plusieurs agents avec points de contrôle humains), GitHub pousse Copilot et l'automatisation « agentic », et surtout **Docker** publie une série d'articles sur la sécurité des agents IA après l'incident OpenAI/Hugging Face et ses ~17 600 actions malveillantes. Le message transverse : *agent security is a systems problem* — la gouvernance des agents ne peut plus reposer sur une revue humaine. HashiCorp et AWS emboîtent le pas avec des agents d'ops (AWS DevOps Agent, Vault agentic security).

Enfin, un vent de responsabilisation souffle sur le stockage CI/CD : **GitHub Actions** aligne la rétention de ses checks, workflow runs et statuses sur la durée de rétention configurée (90 jours par défaut, au lieu de 400+ jours) à partir du 1er octobre — un changement qui va alléger l'empreinte de stockage après des années de données dormantes.

## 🚀 CI/CD

### GitLab 19.2 : l'agent devient citoyen de premier rang

**GitLab 19.2** pousse franchement l'agentification de la plateforme. Deux événements sont passés en **disponibilité générale** :

- **GitLab Duo CLI** — mode interactif en chat *et* mode **headless pour le CI/CD**, avec gestion des modèles, sessions partagées, **approbation d'outils**, connexions **MCP** et support de fichiers de personnalisation (`AGENTS.md`). Pour du Self-Managed/Dedicated, l'activation est contrôlée par l'admin.
- **GitLab Duo custom flows** — des workflows **définis en YAML**, réutilisables par équipe, avec **orchestration multi-agents**, points de contrôle *human-in-the-loop* (HITL) sur les étapes sensibles, déclencheurs natifs GitLab (mentions, assignations, événements de pipeline et de MR), exécution sécurisée via **service accounts & identité composite**, et **validation YAML avant exécution**.

Deux nouveautés bêta côté sécurité complètent l'offre : le **Security Review Flow** et le **rapport d'audit des événements IA** (utile pour l'investigation d'incidents, les revues de conformité et la gouvernance IA). À noter aussi le **non-default branch tracking** (bêta) pour le rapport de vulnérabilités.

> **Analyse :** les custom flows sont l'évolution la plus intéressante. Le fait de pouvoir exprimer un pipeline d'agents en YAML *validé avant runtime* et de verrouiller les étapes critiques par approbation humaine règle une partie du problème de confiance. Mais la maturité reste à prouver : « multi-agent orchestration » et « composite identity » sont des promesses fortes qui demanderont du recul en production. 👀 à surveiller.

**Côté sécurité (à ne pas rater)** — GitLab a publié en août sa **patch critique 19.2.4** corrigeant une **injection de code via une directive GraphQL** (CVE-2026-19478, **Critical**) et une **CSRF dans le handler multiplex de GraphQL** (CVE-2026-19650, High). La 19.2.2 avait déjà corrigé une **exécution de code à distance via path traversal dans le package registry** (CVE-2026-10053) ainsi que plusieurs XSS et problèmes d'autorisation dans l'API de pipeline CI/CD. **Mettez à jour vos instances rapidement.**

### GitHub Actions : la rétention se durcit (et ça réduit la facture)

Le changement le plus structurant du mois sur GitHub est l'**alignement de la rétention** : à partir du **1er octobre 2026**, les *checks*, *workflow runs* et *statuses* seront soumis à la même durée de rétention que les artefacts et logs (90 jours par défaut), alors qu'ils étaient conservés **400+ jours** jusqu'ici. Conséquences concrètes :

- le libellé du paramètre devient « Check, workflow run, status, artifact and log retention » ;
- pour les repos publics, la rétention max sur ces métadonnées est **plafonnée à 90 jours** ;
- le changement est **non rétroactif** ;
- les artefacts et logs comptant dans le stockage facturable, les repos qui conservaient trop longtemps verront leur **facture baisser**.

C'est un gain de coût indirect, mais un changement de comportement à anticiper : si vous exploitez des données de workflow sur des fenêtres longues (audit, rapprochement), **augmentez la rétention avant le 1er octobre**.

Autres avancées GitHub : l'**image `windows-11-arm64` VS2026 passe en GA** (20 août) — un vrai plus pour les runners Windows natifs ARM —, et **GitHub Enterprise Server 3.22 est en RC** (11 août). Côté migration inter-plateforme, l'outil **GitHub Enterprise Importer** (augmente l'offer de migration) prend désormais en charge **la migration depuis GitLab**.

> **Analyse :** l'image `windows-11-arm64` est un vrai pas en avant pour les pipelines Windows cross-compilés ; la rétention, elle, est un « coup de balai » pragmatique mais il faudra vérifier que vos jobs d'audit n'en dépendent pas. ✅ impactant (rétention) / ⚪ anecdotique (image ARM pour beaucoup de boîtes).

### Jenkins : coup de balai sur l'héritage Windows

Jenkins a annoncé la **fin des images de conteneurs d'agents basées sur Windows Server 2019**, effective au **21 août 2026** — le support avait déjà été retiré du cœur dans Jenkins 2.569 / 2.568.1. Les agents inbound et SSH doivent migrer vers une base Windows plus récente. Dans le même temps, la communauté poursuit son travail sur le **Plugin Modernizer** (GSoC 2026) et publie le plugin du mois d'août : le **Dark Theme Plugin**. Un **Contributor Summit virtuel** est annoncé au **11 septembre 2026**.

> **Analyse :** la fin de Windows Server 2019 est une dépréciation logique mais qui impose un plan de migration. ⚪ anecdotique pour ceux qui sont déjà sur Server 2022+ ; ✅ à traiter pour les autres.

## 🐳 Conteneurisation & Orchestration

### Kubernetes v1.37 « Garhwal » : la maturité par le nettoyage

Sortie le 26 août après 15 semaines de cycle, avec plus de **1 700 contributeurs** et **212 entreprises**. 67 améliorations. Contexte : 66 % des orgs servant de l'IA générative utilisent déjà Kubernetes.

**Passé en stable (GA) :**
- **Metrics API (`metrics.k8s.io`)** — après **neuf ans en bêta** ! Le socle de `kubectl top` et de l'autoscaling par métriques est enfin officiel, sans changement fonctionnel attendu.
- **Pod-level resources (KEP-2837)** — définir CPU/mémoire au niveau du **pod entier**, pas seulement par conteneur. Un vrai gain pour les pods à sidecars : un budget partagé au lieu de gonfler chaque conteneur au pire cas.
- **Pod Certificates (KEP-4317) + ClusterTrustBundles (KEP-3257)** — l'histoire d'identité de workload par excellence : les pods obtiennent des certificats X.509 via une API `PodCertificateRequest` + volume projeté, et les clusters exposent des ancres de confiance en objet natif. Si vous utilisez un mesh ou cert-manager *juste* pour distribuer des certificats, les primitives natifs sont là.
- **KYAML (`kubectl get -o kyaml`)** — format « pretty-print » YAML, stable et conforme. Chaque fichier KYAML reste du YAML valide → **aucun changement de pipeline requis**.
- **SELinuxMount / SELinuxChangePolicy** — stables et **activés par défaut** : les volumes sont montés avec `-o context=<label>` au lieu d'un relabeling récursif.
- **Watch cache resilient** — le gate `WatchCacheInitializationPostStartHook` complète le travail entamé en v1.34.

**Bêta (impactant votre facture) :**
- **HPA scale to zero** — activé **par défaut** ! Avec `spec.minReplicas: 0` et des métriques objet/externes, un HPA peut descendre à **0 pod** au repos puis remonter. Interdit pour les métriques CPU/mémoire (qui ont besoin de pods actifs pour être mesurées). Un record de condition `ScaledToZero` distingue « scaling auto vers 0 » d'un « réplicas mis à 0 à la main ». **Gain direct pour files de messages, batchs et workloads GPU.**
- **Admission control par manifeste** — webhooks d'admission et politiques CEL chargés depuis des fichiers disque (`staticManifestsDir`), applicables dès le démarrage de l'API server, fonctionnant même si etcd est indisponible.

**Alpha & dépréciations (à surveiller):**
- **Pod-level checkpoint & restore (KEP-5823)** — checkpoint complet de pods pour restauration ultérieure.
- **DRA (Dynamic Resource Allocation)** — le côté « requête » du partage GPU monte en upstream.
- **Dépréciations qui font mal :** `kube-proxy` en mode **ipvs** est formellement déprécié (retrait prévu en 1.43) ; les nœuds **cgroup v1** échouent à démarrer kubelet sans opt-out explicite. **Auditez vos clusters avant de rouler.**

> ⚠️ **Piège connu (attention à reproduire) :** SELinuxChangePolicy activé par défaut peut casser des pods partageant un volume avec des labels SELinux différents (qui cohabitaient sous le relabeling récursif). Solution : repasser à `.spec.seLinuxChangePolicy: Recursive` sur le pod. Vérifiez vos graduations sur les **fichiers KEP (`kep.yaml`)**, pas sur les blogs — au moins un récapitulatif largement partagé a présenté le **serializer CBOR** comme stable alors qu'il est **bêta**.

### Gateway API v1.6 : les routes TCP/UDP se normalisent

La v1.6.0 (sortie le 30 juin, détaillée le 3 août) fait passer **TCPRoute et UDPRoute en Standard**. Le networking orienté rôle prend ses distances avec les Ingress classiques et devient la référence pour le trafic non-HTTP (gRPC, mTLS, etc.).

> **Analyse :** Kubernetes v1.37 est probablement la release la plus « assainissante » depuis des années. Les gains concrets (Metrics API, pod-level resources, HPA scale to zero) sont réels et directement actionnables ; les dépréciations (ipvs, cgroup v1, kubelet) vont demander un plan de migration. ✅ Très impactant.

### Docker : la sécurité « zero CVE » et les agents IA

Docker a recentré son discours sur la **sécurité par défaut** et la **confiance logicielle** :

- **« Make zero CVEs your new default »** (17 août) : plus de logiciels construits depuis les sources dans les images, couverture de sécurité maintenue **au-delà de la fin de vie**, garanties transportées dans les images customisées, et **application de politiques directement sur la machine du développeur**.
- **Migration depuis Minimus** : le registre **Minimus ferme le 22 octobre** — Docker propose un chemin de migration vers **Docker Hardened Images** et de l'aide gratuite.
- **Docker ELS (Extended Lifecycle Support)** pour les logiciels EOL type **MinIO** (fin de vie février 2026) : 5 ans de correctifs et conformité d'audit.
- **Docker Verified Publisher (DVP) en self-serve** (20 août) : les éditeurs peuvent candidater directement via Docker Hub.
- **Docker Sandboxes dans GitHub Actions** (21 août) : exécution d'agents IA isolés capables de lancer des tests Testcontainers, corriger du code et ouvrir des PR.

L'article le plus notable est **« AI Agent Security Is a Systems Problem »** (18 août), qui décompose l'incident **OpenAI/Hugging Face** : **~17 600 actions d'attaquants** pour montrer que la sécurité des agents ne peut pas s'appuyer sur la revue humaine seule — il faut des contrôles pour **contraindre, observer et gouverner** les agents à grande vitesse.

> **Analyse :** le positionnement de Docker sur l'agent-sécurité est pertinent mais commercialement opportuniste (il vend des sandboxes). La baisse de la confiance (Minimus, MinIO EOL) rappelle qu'il faut vérifier la **pérennité de vos registres**. ✅ impactant (hardened images, sandboxes) / ⚪ anecdotique (DVP self-serve).

## 🏗️ Infrastructure as Code

### HashiCorp : Terraform + Ansible, Boundary 1.0, et l'agentic security

HashiCorp a livré plusieurs avancées structurantes :

- **Terraform Ansible Collection 2.0** + **pyTFE** + une expérience **Terraform Actions** améliorée pour simplifier la gestion du cycle de vie de l'infra entre Terraform et Ansible. C'est une reconnaissance que Terraform (provisioning) et Ansible (configuration) se complètent — la frontière IaC/config devient plus fluide.
- **Boundary 1.0** : support de **l'enregistrement de session RDP** et aperçu de la sécurisation de l'accès des agents IA.
- **HCP Vault Dedicated** : **disaster recovery au niveau cluster** (public preview) — des exercices de DR au niveau du cluster pour simuler des pannes et prouver la capacité de failover.
- **HCP Packer** : **enforced provisioners** — application centralisée d'étapes de provisionnement obligatoires sur les builds d'images.
- **Vault Enterprise** : renforcement de la **sécurité des agents IA** (public preview) — gestion d'identité et d'accès des agents.
- **Azure hub-and-spoke** en GA pour HCP Vault Dedicated (connectivité privée).

> **Analyse :** l'alliance Terraform/Ansible est mature et bienvenue ; la DR au niveau cluster et les enforced provisioners sont des signaux d'un HashiCorp qui monte en gamme « enterprise ». Les features « agentic security » sont à suivre mais encore en preview. ✅ impactant (Ansible collection 2.0, Packer enforced provisioners) / 👀 à surveiller (agentic identity).

### AWS : agents, drift, et MCP pour l'IaC

Le blog DevOps AWS du mois est très orienté **agents et réseau/iaC** :

- **AWS DevOps Agent + un Kubernetes Operator** pour l'EKS (31 août) : réduction du **MTTR** en automatisant la collecte de logs et le triage d'incidents type `OOMKilled` / épuisement d'IP.
- **Du clickops à l'IaC gouvernée : détection de drift CloudFormation** — le cas des environnements « organiques » provisionnés à la console sans template.
- **IaC MCP Server pour CloudFormation** (4 août) : authoring, validation, déploiement et troubleshooting **depuis votre assistant IA**.
- **SageMaker HyperPod** : triage d'incidents et RCA automatisés avec AWS DevOps Agent (10 août).
- **AWS DevOps Agent + ServiceNow** pour des opérations autonomes (corrélation contextuelle).
- **AWS DevOps Agent + CodePipeline/GitHub** pour réduire les heures de debug des échecs CI/CD.

> **Analyse :** AWS confirme sa stratégie « agent d'ops » couplée à l'assistant IA. L'IaC MCP Server est un exemple très concret d'où va le tooling : le niveau de l'infra s'écrit désormais depuis le LLM. ✅ impactant, mais attention à la maturité (beaucoup de « 300/400 level » opérés par agents).

## 🔭 Observabilité & DevSecOps

### Agents, SRE et IA : le thème central du mois

InfoQ s'est fait l'écho de plusieurs réalisations majeures en observabilité et fiabilité :

- **« Can Claude Fix Itself? Using LLMs for Incident Response »** (présentation Anthropic, Alex Palcuie) : là où les LLM sont **supérieurs** — observer logs et traces — et là où ils **échouent** — la causalité vs corrélation dans l'analyse de cause racine. Leçon : intégrer l'IA dans l'on-call **sans éroder l'expertise humaine**.
- **Netflix adopte Kueue** (file d'attente de jobs cloud-native Kubernetes, CNCF) pour remplacer une solution interne de batch processing.
- **DoorDash** exécute **130 000 tâches d'ingénierie** via des agents cloud "Flux".
- **Uber construit GitFarm** : git operations as a service pour ses **monorepos** à grande échelle.
- **AWS open-source Kiro Crew** (agents de code asynchrones).
- **MCP passe en stateless** — et les développeurs se demandent si ça ne le ramène pas à une simple API.
- **AKS : nouvelle guidance NAP** pour rendre les disruptions de nœuds plus prévisibles.

Côté sécurité/DevSecOps :
- **Windows 11 arm64 VS2026** (cf. CI/CD) et l'audit log pour le **Code Quality enablement**.
- **Code scanning** : raison de rejet « mitigated » ajoutée.
- **CodeQL 2.26.2** (Swift 6.3.3, Kotlin 2.4.10) et **2.26.3** (requêtes Actions + modélisation JS).
- **Secret scanning** : couverture étendue (7 août).
- **Dependabot** : personnalisation des noms de branches de PR (4 août).
- **GitHub** : migration automatique des **branch protection rules** vers les **repository rulesets** (11 août) — l'alignement modernisation/consolidation continue.
- **BMC vulnerabilities** : des milliers de serveurs exposés à une compromission au niveau matériel.

### Bonnes pratiques émergentes

1. **Traiter la sécurité des agents comme un système, pas une revue** : contraindre (sandbox, permissions), observer (logs structurés, audit trail), gouverner (politiques, HITL sur étapes sensibles). Le framework « sandbox + boundary + contrôle » de Docker est une bonne colonne vertébrale.
2. **Vérifier la pérennité de vos registres/miroirs d'images** : fermetures (Minimus) et EOL (MinIO) poussent à l'**image hardenée** et au **SBOM**.
3. **Prendre les dépréciations Kubernetes au sérieux** : `kube-proxy ipvs`, **cgroup v1**, SELinuxChangePolicy par défaut. **Testez sur un cluster de staging** avant le grand saut.
4. **Ne pas se fier aux blogs pour les graduations de fonctionnalités** — auditiez les `kep.yaml`. (Le « CBOR stabilisé » est en réalité bêta en 1.37.)
5. **Anticiper la fin de la rétention longue GitHub Actions** : revoir la politique avant le 1er octobre si vous avez besoin de données de workflow historiques.

### Exemples de configuration

**HPA scale to zero (Kubernetes 1.37 bêta)** — fichier queue consommera 0 pod au repos :

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: queue-worker-scaled-to-zero
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: queue-worker
  minReplicas: 0        # <- scale to zero
  maxReplicas: 10
  metrics:
    - type: Object
      object:
        metric:
          name: queue_depth
        describedObject:
          apiVersion: apps/v1
          kind: Deployment
          name: queue-worker
        target:
          type: Value
          value: "10"
```

**Pod-level resources (K8s 1.37 stable)** — budget partagé pour un pod à sidecars :

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: app-with-sidecar
spec:
  resources:                # <- KEP-2837 : budget au niveau du POD
    requests:
      cpu: "500m"
      memory: "512Mi"
    limits:
      cpu: "1"
      memory: "1Gi"
  containers:
    - name: app
      image: nginx:1.27
    - name: sidecar
      image: busybox:1.36
```

**Contournement SELinux** (si un pod partageant un volume ne démarre plus) :

```yaml
apiVersion: v1
kind: Pod
spec:
  securityContext:
    seLinuxChangePolicy: Recursive   # <= restaure l'ancien comportement
```

**GitLab Duo custom flow (19.2)** — workflow YAML avec point de contrôle humain :

```yaml
# .gitlab/duo-flows/release-review.yml
flow:
  name: security-review
  stages:
    - id: scan
      agent: security-agent              # SAST / dependency scanning
    - id: human-gate
      type: human-in-the-loop            # approbation obligatoire
      approvers: [security-lead]
    - id: package
      agent: release-agent
      service_account: ci-release        # identité composite
```

## 🔮 Mises en perspective & impact roadmap

Trois tendances se dégagent pour votre roadmap :

1. **Plateforme = confiance & nettoyage.** K8s 1.37 montre une maturité assumée (Metrics API GA, retrait d'héritage). Cela signifie qu'il faut **auditer vos clusters** (ipvs, cgroup v1, SELinux) et intégrer les primitives natifs de sécurité (Pod Certificates, ClusterTrustBundles) — peut-être au détriment de briques externes type cert-manager.
2. **Agents partout, gouvernance partout.** GitLab Duo, GitHub Copilot, AWS DevOps Agent, Docker Sandboxes : l'orchestration agentique devient le nouveau front de l'ingénierie. Le point dur n'est plus la génération mais la **sécurité et le contrôle** (HITL, service accounts, audit trail, sandbox). À intégrer dès que possible dans vos pipelines — c'est là que se joue la différence de coût et de sécurité.
3. **Qui sème la donnée récolte la facture.** La rétention GitHub Actions, la fermeture de Minimus, l'EOL de MinIO : l'écosystème se responsabilise sur les coûts et la pérennité. Planifiez une **politique de rétention et de provenance d'artefacts** (SBOM, signatures) si ce n'est pas déjà le cas.

**À surveiller de près :** le *stateless MCP* et ses implications sur la sémantique d'API ; les dépréciations Kubernetes pour 1.40-1.43 (ipvs → 1.43) ; la maturité réelle des custom flows GitLab et de l'agentic identity HashiCorp.
