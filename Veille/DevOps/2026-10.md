# Veille DevOps – Octobre 2026

## Synthèse du mois

Octobre 2026 restera comme **le mois où une autorité de certification a cassé la confiance de toute la chaîne d'outils**. Le 17 octobre, un chercheur annonce avoir récupéré les clés privées de **huit certificats intermédiaires eMudhra** : lors d'une cérémonie de génération de clés le 30 avril 2025, un défaut du processus a produit des clés P-384 avec **3 à 8 bits d'entropie effective** au lieu de 384. Récupérer la clé privée tient alors du calcul trivial, et qui la détient peut émettre un certificat valide pour n'importe quel domaine. Chrome, Mozilla, Apple et Microsoft ont bloqué les certificats ; eMudhra a révoqué et arrêté d'émettre sous sa racine G3. Mais le vrai séisme est en aval : parce que **Go embarque son propre moteur de vérification X.509** et ignore souvent la révocation, l'équipe Go a dû traiter l'incident comme une vulnérabilité (CVE-2026-111943) et publier **Go 1.27.3 et 1.26.10**. En cascade, en deux semaines, il a fallu republier Docker Engine, GitLab, GitLab Runner, AI Gateway, Terraform, le Collector OpenTelemetry, les images PHP… Un rappel brutal : dans un pipeline, « la sécurité TLS » n'est pas un service rendu par l'OS, c'est **un binaire compilé dans chaque outil que vous exécutez**.

Deuxième fil rouge, plus classique : **deux RCE critiques dans les outils qui pilotent le déploiement**. GitLab publie le 21 octobre un correctif pour **CVE-2026-110264, CVSS 10.0** — un débordement d'entier dans le compilateur d'expressions régulières permettant à un utilisateur **non authentifié** d'exécuter du code arbitraire sur le serveur, toutes versions depuis la 7.0 concernées. Le 6 octobre, Argo CD corrige **huit failles dont quatre à CVSS 9.9**, la plus intéressante étant un contournement d'autorisation sur les hooks `PostDelete` : celui qui a le droit d'écrire dans le dépôt Git d'une Application peut y glisser un hook qui crée un `ClusterRoleBinding` avec les credentials du controller. Et le 20 octobre, **PHP2Shell** (CVE-2026-109618 / 109619) ajoute une RCE dans le cœur de PHP, toutes branches depuis la 5.4. Trois rappels que la surface d'attaque d'une plateforme DevOps, ce n'est pas le code applicatif : c'est **le plan de contrôle**.

Troisième mouvement, plus structurant : **le pipeline devient un artefact vérifiable et gouverné**. GitHub passe ses **workflow lockfiles en GA** (28 octobre) — on garde des tags lisibles dans le YAML, on exécute les commits verrouillés, et Dependabot resynchronise le lockfile dans la même PR. Terraform 1.17 rend **Terraform Policy GA** : les politiques s'évaluent dans `plan`, `apply` et `query`, sans build expérimental. GitLab livre son **Secrets Manager GA** (adossé à OpenBao) et un **serveur MCP GA** pour brancher des agents externes sous la même identité et les mêmes politiques. Le fil conducteur : après avoir passé deux ans à automatiser, l'écosystème passe à **verrouiller et prouver** ce qui s'exécute.

## 🚀 CI/CD

### GitHub Universe : le pipeline devient un objet verrouillé

Annoncé à Universe (28-29 octobre, San Francisco), le changement le plus important pour une équipe plateforme n'est pas le plus spectaculaire : ce sont les **workflow lockfiles en GA**. Le problème qu'ils règlent est vieux comme `uses: action@v3` : un tag peut bouger après votre revue, et un tag déplacé suffit à injecter du code dans votre pipeline sans aucun commit chez vous.

Le fonctionnement est celui de `npm ci` transposé aux Actions :

```bash
# 1. Générer le lockfile (actions + dépendances transitives)
gh extension install github/gh-actions-lock
gh actions-lock generate

# 2. Le workflow garde ses tags lisibles, l'exécution utilise les commits verrouillés
#    -> .github/workflows/actions.lock est commité
git add .github/workflows/actions.lock .github/workflows/*.yml

# 3. Vérifier en CI que rien n'a dérivé (sans modifier de fichier)
gh actions-lock check --fail-on-stale
```

Trois propriétés à retenir : l'adoption se fait **workflow par workflow** (une fois un workflow « onboardé », GitHub exige que **toutes** ses dépendances soient dans le lockfile) ; **Dependabot régénère l'entrée correspondante dans la même PR** de mise à jour, sans configuration supplémentaire ; et les admins peuvent imposer la politique **« Require lockfile »** au niveau repo, orga ou enterprise. La limite est explicitement documentée par GitHub : un lockfile protège contre le **déplacement** d'une dépendance, pas contre sa **compromission** — il faut donc toujours revoir ce qu'on verrouille.

Deuxième chantier : **GitHub Agentic Workflows passe en GA**. On décrit l'automatisation en Markdown, elle est compilée en YAML Actions standard, donc elle hérite des runner groups et des politiques existantes — et on peut mettre Copilot **ou** son propre agent derrière. Le détail qui compte pour une équipe sécurité : un **job de détection de menaces** analyse ce que l'agent propose avant application, et le support ARC + Docker-in-Docker est arrivé avec la GA.

Troisième point, celui qui va casser des choses en silence : **Actions répartit désormais les jobs sur un pool multi-cloud**. Objectif affiché : moins de files d'attente, plus de résilience en pic de demande. Conséquence opérationnelle immédiate, et GitHub la signale sans détour : les runners du pool étendu utilisent **de nouvelles adresses IP sortantes**. Toute allowlist qui n'autorise que les plages Azure/Microsoft — y compris des politiques **Microsoft Entra Conditional Access** — bloquera l'authentification de ces runners. À traiter avant que les jobs ne commencent à y tourner, puisque le déploiement est progressif.

Compléments du mois : **ARC 0.15.0** (1er oct.), image runner **Xcode 27 en GA** (15 oct.), **retrait de macOS 14** (1er oct.), et **tokens d'installation GitHub App sans état** (2 oct.), qui simplifient l'authentification des intégrations.

> **Analyse :** ✅ Très impactant (lockfiles GA) — c'est la première réponse crédible au risque « tag mouvant » sans imposer des SHA illisibles partout. ✅ Impactant (multi-cloud + allowlists) : zéro changement de YAML, un risque de panne réel. 👀 À surveiller (Agentic Workflows) : puissant, mais à encadrer par la politique de permissions avant de laisser un agent toucher aux PR. ⚪ Anecdotique (Xcode 27, macOS 14).

### GitLab 19.5 et la douche froide du 21 octobre

La release du 15 octobre est sage : les **permaliens de lignes de code** s'affichent désormais en extrait coloré (avec chemin et commit) au lieu d'une URL brute dans les MR et les wiki — petite chose, gros gain de contexte en revue. Surtout, GitLab a empilé **trois GA en octobre** : **Secrets Manager** (adossé à **OpenBao**, secrets scoppés au job, limités par branche/environnement/statut de protection, avec audit — et retrait automatique des accès lors d'un offboarding), **serveur MCP** (les agents externes atteignent projets, MR, work items et pipelines sous la même identité et les mêmes politiques), et **Orbit** le 29 octobre — un graphe qui relie code, MR, pipelines, findings de sécurité et ownership. GitLab annonce **jusqu'à 45× moins de retries** pour les agents qui l'interrogent, et l'usage le plus parlant est le *blast radius* d'un CVE : « quels projets, propriétaires et pipelines cette faille touche-t-elle ? » en une requête au lieu d'une chasse manuelle.

Puis le 21 octobre, GitLab publie un patch **critique** : **CVE-2026-110264**, **CVSS 10.0**. Un débordement d'entier à la compilation d'une expression régulière spécialement construite permet à un utilisateur **non authentifié** d'exécuter du code arbitraire sur le serveur GitLab. Toutes les versions depuis la **7.0** sont concernées — GitLab a backporté jusqu'à la 18.11.13. Deux détections de menace sont fournies pour les instances self-managed (*Onigmo native worker crash*, *Org mode render error burst*) : autrement dit, GitLab s'attend à des tentatives d'exploitation, pas à de la théorie. Dans le même patch : CVE-2026-15723 (CVSS 8.2, prise de contrôle d'un compte LDAP via auto-linking OmniAuth) et CVE-2026-112212 (CVSS 7.5, empoisonnement du cache de découverte OIDC).

Fin octobre, le patch eMudhra ajoute une subtilité que beaucoup d'équipes vont rater : **mettre à jour GitLab ne suffit pas**. Le **Runner** vérifie les certificats lui-même (il faut la 19.5.1) et l'**AI Gateway** aussi (18.11.8 / 19.0.13 / 19.1.9 / 19.2.5 / 19.3.3 / 19.4.3 / 19.5.3). Et toute image de job qui embarque son propre paquet `ca-certificates` doit être **reconstruite**, sinon elle continuera de faire confiance aux intermédiaires compromis.

> **Analyse :** ✅ Critique (CVE-2026-110264) — CVSS 10.0, non authentifié, sans interaction : patch ou exposition. ✅ Impactant (Secrets Manager GA) : enfin des secrets CI qui suivent le cycle de vie des permissions GitLab. 👀 À surveiller (Orbit) : très prometteur pour le triage CVE, mais dépend de la qualité de votre graphe (ownership à jour).

### Jenkins : LTS 2.580.2, et un WAR qui maigrit

La LTS **2.580.2** (28 octobre) embarque des **correctifs de sécurité importants**, plus Jetty 12.1.14 via Winstone et Stapler, et une mise à jour de `handlebars` (4.7.10). Le changement de fond date de la 2.580.1 (30 septembre) mais se déploie avec elle : Jenkins **a cessé d'embarquer une douzaine de plugins** (bouncycastle API, Command Agent Launcher, JAXB, Trilead API, SSH server, JAF, JavaMail, Instance Identity, JUnit, Mailer, Matrix Authorization Strategy, Matrix Project, OWASP Markup Formatter) — **plus de 20 Mo de `jenkins.war` en moins**, deux fois. Les configurations anciennes ne sont plus migrées automatiquement : si votre instance vient de 2.356 ou avant, il faut installer ces plugins à la main. À vérifier avant de mettre à jour, sinon l'authentification ou les agents tombent.

Côté hebdomadaire, la ligne 2.586 est sortie le 15 octobre, et la LTS exige désormais **JDK 21 ou 25** (plateformes testées : Linux, Windows).

> **Analyse :** 👀 À surveiller (retrait des plugins bundlés) : gain de taille réel, mais piège de migration pour les vieilles instances. ✅ Impactant (correctifs de sécurité LTS) : à appliquer, comme chaque mois.

## 📦 Conteneurs & orchestration

### Kubernetes : le cycle 1.38 se cale, la 1.34 s'éteint

Pas de release majeure en octobre — la 1.37.1 est sortie le 15 septembre et le cycle suivant est déjà lancé :

- **1.38.0-alpha.2** le 7 octobre, **alpha.3** le 21 octobre ;
- **enhancements freeze** passé le 30 septembre (le périmètre est figé) ;
- **feature blog freeze** le 5 novembre, **KubeCon NA** du 9 au 12 novembre (Salt Lake City), **code freeze** le 17 novembre ;
- **1.38.0 attendue le 16 décembre**.

Et une échéance qui est tombée ce mois-ci : **Kubernetes 1.34 est EOL depuis le 27 octobre** (dernier patch 1.34.12). Les lignes supportées sont désormais **1.35, 1.36 et 1.37** — si vous êtes encore en 1.34, vous ne recevez plus de correctifs de sécurité.

Le billet le plus utile du mois est celui sur **cgroup v2** (6 octobre), parce qu'il annonce une rupture de démarrage : depuis la **1.35**, `failCgroupV1` vaut **`true` par défaut**, donc **le kubelet ne démarre plus** sur un nœud en cgroup v1. kubeadm a même durci le contrôle : la vérification `SystemVerification` échoue en `init`, `join` et `upgrade` avec un kubelet ≥ 1.35.

```yaml
# /var/lib/kubelet/config.yaml
# Solution TEMPORAIRE pour un parc encore partiellement en cgroup v1.
# À retirer : le retrait complet est suivi dans KEP-5573.
failCgroupV1: false
```

```bash
# Vérifier ce qui reste réellement en v1 avant de planifier la montée
for n in $(kubectl get nodes -o name | cut -d/ -f2); do
  echo "$n: $(kubectl get --raw /api/v1/nodes/$n/proxy/configz | jq -r '.kubeletconfig.cgroupDriver')"
done
stat -fc %T /sys/fs/cgroup   # cgroup2fs = v2
```

Le billet rappelle aussi un piège classique qui **ne disparaît pas** avec v2 : le kubelet considère `active_file` comme non récupérable, donc une charge très I/O peut déclencher des évictions sur un gros page cache (kubernetes#43916). Le contournement documenté reste de fixer des **requests = limits** sur les conteneurs intensifs en I/O, après mesure.

Deux autres billets méritent le détour : **Node Swap pour absorber les pics mémoire** (5 octobre) — les charges d'IA agentique démarrent gros et retombent, exactement le profil où le swap bien configuré évite des OOMKill — et le tracing d'admission **Kueue** avec **Headlamp** (14 octobre), qui répond à la question la plus frustrante du batch : « pourquoi mon Job reste-t-il `Pending` sans Pod ni log ? ».

Côté gouvernance, la communauté a créé un **Workload Conformance Working Group** (27 octobre) : un standard partagé de *comportement à l'exécution* des workloads, et un sous-projet **AI Conformance** rattaché à SIG Architecture (29 octobre). À suivre : c'est le socle sur lequel les plateformes internes pourront affirmer « ce workload se comporte pareil partout ».

> **Analyse :** ✅ Très impactant (EOL 1.34 + `failCgroupV1`) — deux échéances fermes, une seule action : migrer en cgroup v2 puis monter de version. ✅ Impactant (Kueue/Headlamp) : gain de temps réel sur le debug batch. 👀 À surveiller (Workload Conformance) : intéressant si vous opérez une plateforme interne multi-tenant.

### Docker Engine 29.9 : une release de sécurité qui ne dit pas son nom

La **29.9.0** (8 octobre) est arrivée après deux RC et se lit comme une release de sécurité : correction de **quatre CVE HTTP/2 côté Go** (dont un crash serveur par course sur l'encodeur HPACK, CVE-2026-97032), **BuildKit 0.34.0**, **containerd 2.4.1**, **Go 1.26.9**, **RootlessKit 3.2.0**, plus une série de correctifs réseau — nettoyage de la chaîne `DOCKER-INGRESS`, fuite de SA IPsec sur l'overlay chiffré, entrées FDB dynamiques, IPv6 Neighbour Discovery et ports publiés. Le **lazy-pull est activé par défaut** pour nydus/overlaybd/soci/stargz : sur un cluster qui tire de grosses images, le temps de démarrage change sans que vous ayez touché à un manifest.

La **29.9.2** (20 octobre) ajoute une mise à jour du runtime Go et du packaging. Et le 20 octobre justement, **PHP2Shell** est tombé : Docker a publié dans les 24 h des **Docker Official Images** et **Docker Hardened Images** corrigées (8.2.35, 8.3.36, 8.4.27, 8.5.12), après passage de sa chaîne de test DHI. C'est le bon exemple de ce qu'on attend d'un registre : la correction arrive au niveau de l'image, pas seulement du paquet.

Rappel de terrain, souvent oublié lors d'une montée en 29.x : l'API passe en **1.52** et le daemon **refuse les clients sous l'API v1.44**. Les panneaux de gestion anciens (Portainer < 2.33.5, par exemple) tombent en « client is too old ».

> **Analyse :** ✅ Impactant (CVE Go/HTTP-2 + lazy-pull par défaut) : à planifier, pas à subir. 👀 À surveiller (API 1.52) : casse silencieuse des vieux clients API. ⚪ Anecdotique (correctifs réseau ciblés).

### Argo CD : huit failles, quatre critiques, et la 2.x laissée pour compte

Le 6 octobre, Argo CD publie **3.5.4, 3.4.10, 3.3.15 et 3.6.0-rc2** pour corriger **huit failles, dont quatre à CVSS 9.9**. Trois touchent le **repo-server**, c'est-à-dire le composant qui construit les manifests — donc celui qui a les credentials Git, Helm et OCI.

La plus instructive est **CVE-2026-77459** (GHSA-fmxq-cgp8-87wp) : lors d'un sync, les hooks `PreSync`, `Sync`, `PostSync` et `SyncFail` passent bien par les contrôles de l'AppProject (allow/deny lists de destinations et de ressources). Les hooks **`PreDelete`/`PostDelete`**, non. Un utilisateur qui a le droit d'écrire dans le dépôt Git d'une Application peut donc y committer un hook de suppression visant un namespace, un serveur ou une ressource interdite, puis supprimer l'Application : le controller crée la ressource avec **ses propres credentials de destination**. Impact borné par les droits du controller, mais suffisant pour un `ClusterRoleBinding` en cluster-scoped. Le correctif fait passer `destCluster` dans `executePreDeleteHooks` pour appliquer l'autorisation projet.

Deuxième faille notable : **CVE-2026-55797**, injection de commandes via l'URL de proxy d'un dépôt Git SSH — l'hôte et le port du proxy sont concaténés dans un `ProxyCommand` exécuté par un shell sans neutralisation des métacaractères. Ouvert à quiconque peut créer ou modifier un dépôt ou un template de credentials.

Le point qui fâche : **la ligne 2.x, ainsi que 3.0, 3.1 et 3.2, ne recevront pas de correctif**. L'upgrade target est 3.3 minimum, à une version patchée. Deux patches de suite ont suivi (3.5.5/3.4.11/3.3.16 le 12 octobre, puis 3.5.6 aux alentours du 20-22), et la **3.6 GA est planifiée pour le 3 novembre** — avec, à cette date, la **3.3 qui sort du support** (règle des trois dernières mineures).

```yaml
# Vérification rapide : des hooks PostDelete qui sortent du périmètre du projet
# (à lancer dans les dépôts qui portent vos Applications)
grep -rn "PostDelete" --include="*.yaml" . | while read -r f; do
  echo "== $f"; yq '.metadata.annotations["argocd.argoproj.io/hook-delete-policy"], .kind' "$f"
done
```

> **Analyse :** ✅ Critique (CVE-2026-77459 + 3 × 9.9) — un dépôt Git n'est pas une frontière de sécurité, et Argo CD vient de le démontrer. ✅ Impactant (fin de support 2.x/3.0-3.2) : dette à traiter, pas à reporter. 👀 À surveiller (3.6 GA le 3 novembre) : lire les notes de montée avant, la 3.3 sortant du support à la même date.

## 🏗️ Infrastructure as Code

### Terraform 1.17 : la politique entre dans le plan

**Terraform 1.17.0** est sorti le **21 octobre** (rc1 le 7, rc2 le 14). Trois nouveautés, une seule qui change vraiment l'organisation :

**Terraform Policy est GA.** Le flag `-policies` de `plan`, `apply` et `query` ne nécessite plus de build expérimental ni `-allow-experimental-features`. Les **query policies** évaluent les ressources découvertes par les blocs `list` et produisent un résultat lisible ou du JSON — autrement dit, on peut poser des règles sur ce qui **existe déjà**, pas seulement sur ce qui va être créé. Pour une équipe plateforme, c'est la différence entre « on interdit dans le code » et « on constate et on alerte sur le réel ».

```hcl
# 1.17 : variables et locals autorisés dans required_providers
# -> fini les versions de provider dupliquées dans chaque module
variable "provider_version" {
  type    = string
  default = "~> 6.0"
}

terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = var.provider_version
    }
  }
}
```

**`-minimal-refresh`** : le refresh ne porte plus que sur les ressources qui ont un changement proposé. Sur un gros state, c'est la différence entre une planification de dix minutes et une de deux — à manier avec la prudence habituelle (un drift hors périmètre ne sera pas vu pendant ce plan).

Le troisième point est organisationnel : Terraform continue de **resserrer le périmètre de ses garanties de sécurité** (le CVE-2026-78669 sur l'épuisement de ressources HTTP/2 ne concerne que les registries compromis, explicitement hors périmètre), et **1.16.7 / 1.17.1** sont surtout là pour Go 1.26.10 et le retrait des CA eMudhra.

Côté alternative, **Pulumi 3.273.0** (28 octobre) ajoute `resourceExists` (vérifier qu'une ressource existe **sans l'adopter** dans le stack) et `up`/`logs` dans les automation APIs Node/Python/Go. Deux commandes dépréciées disparaissent (`pulumi watch`, `pulumi logs` nu), et un détail révélateur de l'époque : Pulumi **ne crée plus automatiquement de compte Cloud pour un agent IA** sauf si `PULUMI_ENABLE_AUTOMATIC_AGENT_SIGNUP` est défini.

**Ansible core 2.22.0-rc2** clôt la stabilisation du cycle 2.22 ; les lignes 2.21.5 et 2.20.10 restent les versions de production.

> **Analyse :** ✅ Très impactant (Policy GA) : les garde-fous IaC passent du lint au plan, et les query policies ouvrent l'audit du legacy. ✅ Impactant (`-minimal-refresh`) : gain de temps direct sur les gros states. 👀 À surveiller (`resourceExists` chez Pulumi) : utile pour les migrations et l'import sans adoption. ⚪ Anecdotique (Ansible RC).

## 📊 Observabilité

### OpenTelemetry : un Collector qui suit le rythme du runtime

Le Collector continue son train bimensuel : **0.163.0** le 14 octobre, **0.164.0** le 26. Le mouvement intéressant est une **promotion de composants contrib vers le cœur** : le receiver **`file_log`**, le processor **`resource_detection`** et le processor **`transform`** arrivent dans la distribution `otelcol` — signe qu'ils sont jugés assez stables pour être supportés largement. Côté contrib, un **partitioning processor** fait son entrée.

Mais la ligne la plus importante de la 0.164.0 est une ligne de sécurité, et elle boucle l'incident du mois :

> Build des binaires avec **Go 1.26.10**, et exigence d'Alpine `ca-certificates` **20261020-r0** ou plus dans les images. Le bundle mis à jour retire les racines eMudhra, dont `emSign ECC Root CA - G3`.

Autrement dit : si vous épinglez une vieille image de Collector, ou si vous construisez la vôtre sur une base sans `ca-certificates` récent, votre export OTLP continue d'accepter une chaîne qui devrait être refusée. Le contrôle tient en une commande :

```bash
# Ce que voit réellement le binaire, pas ce que voit l'hôte
docker run --rm --entrypoint sh otel/opentelemetry-collector-contrib:0.164.0 \
  -c 'grep -c BEGIN /etc/ssl/certs/ca-certificates.crt; apk info -v ca-certificates 2>/dev/null'
```

### Grafana 13.3 et un correctif à ne pas rater

**Grafana 13.3** (29 octobre) apporte des **variables cross-dashboard** (définies une fois, scopées Global ou Folder — fin de la duplication des sélecteurs environnement/région/cluster), des **Notebooks** en preview (construire un post-mortem depuis des panels), le plus gros **refresh visuel depuis la 7** (sans breaking change annoncé pour les plugins) et les **dashboard plans** de Grafana Assistant. Le *Undo turn* de l'Assistant passe en GA.

À traiter en parallèle : **CVE-2026-100105** (CVSS 7.7), un contournement d'autorisation sur les contact points via downgrade de schéma, corrigé en **12.4.14, 13.0.12, 13.1.9 et 13.2.5** (13.3 est sain). Quiconque peut éditer un contact point est concerné : à vérifier sur la ligne que vous exploitez, pas seulement sur la dernière.

### Débugger l'admission plutôt que la regarder

Le billet Kubernetes **Kueue + Headlamp** (14 octobre) vaut comme méthode : quand un Job reste `Pending` sans Pod, il n'y a **rien à observer** — ni logs, ni traces, ni métriques applicatives. Le funnel d'admission (quota, priorité, preemption, topology) est un angle mort classique de l'observabilité, et le visualiser vaut mieux qu'empiler des alertes sur `kube_job_status_failed`. Même logique côté GitLab : **Orbit** vend la même idée un cran plus haut — un graphe unique pour répondre à « qui est impacté », plutôt que de corréler à la main cinq outils.

> **Analyse :** ✅ Impactant (promotions core du Collector) : moins de distributions custom à maintenir. ✅ Impactant (CVE Grafana 7.7) : patch sur la ligne active, banale mais réelle. 👀 À surveiller (Notebooks, variables cross-dashboard) : previews utiles, à tester avant standardisation. ⚪ Anecdotique (refresh visuel).

## 🔐 DevSecOps

### L'incident eMudhra : anatomie d'une confiance qui s'effondre

Le récit complet, parce qu'il est instructif de bout en bout.

**Le défaut.** Le 30 avril 2025, eMudhra mène une cérémonie de génération de clés pour 24 CA subordonnées. Un défaut du processus crée un **second jeu de clés P-384 faibles** lors d'une étape de *wrap/unwrap*, et ce sont ces clés-là qui servent à **huit certificats intermédiaires**. L'entropie effective tombe à **3-8 bits** : les clés privées contiennent des entiers à un ou deux chiffres, récupérables sans outil spécialisé. Six intermédiaires sont des CA TLS, deux des CA de signature de code.

**La divulgation.** Le 17 octobre, un chercheur signale la récupération des clés. Chrome, Mozilla et Apple bloquent les six TLS ; Microsoft bloque les deux code-signing ; Google retire `emSign ECC Root CA - G3` du Chrome Root Store ; eMudhra révoque les huit certificats (18 octobre) et arrête d'émettre sous sa racine G3. La CA croisée révoque ses copies le 19.

**Le vrai problème.** Une révocation ne sert à rien si le client ne la vérifie pas. Or **Go implémente sa propre vérification de chaîne** dans `crypto/x509` et s'appuie sur des pools de racines embarqués ou hérités — particulièrement en conteneur statique. Pour couvrir tout l'écosystème cloud-native (**Docker, Kubernetes, Terraform, Prometheus…**), l'équipe Go transforme l'incident en vulnérabilité : **CVE-2026-111943** (et CVE-2026-111944), corrigée dans **Go 1.27.3 et 1.26.10**, qui filtrent les chaînes contenant le **SHA-256 du SubjectPublicKeyInfo** des huit intermédiaires.

**La cascade, en deux semaines.** GitLab (19.5.3 et backports jusqu'à 18.11.14, **plus Runner et AI Gateway**), Terraform (1.16.7, 1.17.0, puis 1.17.1), Docker Engine (29.9.2), OpenTelemetry Collector (0.164.0), les distributions Linux (`ca-certificates`, RHEL 6 à 10, Amazon Linux 2/2023), et la bibliothèque Python **certifi** (GHSA-6q48-6c7w-9gw2).

**Ce qu'il faut en retenir opérationnellement :**

```bash
# 1. Le paquet système est-il à jour ?
rpm -q ca-certificates || dpkg -l ca-certificates

# 2. Le runtime, lui, embarque sa propre logique
go version              # >= 1.27.3 ou >= 1.26.10
terraform version       # >= 1.16.7 / 1.17.1
docker version          # >= 29.9.2

# 3. Les images construites maison embarquent un trust store : à reconstruire
#    (même si l'hôte est patché, l'image garde l'ancien bundle)

# 4. Les certificats feuilles émis par ces intermédiaires doivent être RÉÉMIS
#    (révoquer ne suffit pas : un client qui ne vérifie pas la révocation les accepte)
```

La recommandation la plus contre-intuitive du mois vient d'AWS : les clients qui appliquent une **vérification de révocation fail-closed** (OCSP ou CRL) ne sont pas affectés. La révocation a fonctionné — pour ceux qui la vérifiaient. Tout le reste a eu besoin d'un patch de trust store.

> **Analyse :** ✅ Très impactant — c'est l'incident de l'année côté supply chain de la confiance, et il a touché presque tous les outils de cette veille. 👀 À surveiller : les certificats feuilles émis sous ces intermédiaires, souvent oubliés parce qu'ils ne déclenchent aucune alerte CVE.

### PHP2Shell : RCE dans le cœur de PHP

Le 20 octobre, deux failles critiques dans PHP, affectant **toutes les versions depuis la 5.4** (y compris 8.2 à 8.5, et les branches EOL 5.x/7.x/8.0/8.1). Les deux sont des défauts de gestion de la mémoire de requête : dans **CVE-2026-109618**, quand PHP manque de mémoire en cours de requête et abandonne, certains chemins laissent de la mémoire non initialisée que le nettoyage relit ; dans **CVE-2026-109619**, l'état interne pointe vers de la mémoire déjà libérée qu'une requête ultérieure réutilise. Résultat : exécution de code à distance.

Correctifs : **8.5.12, 8.4.27, 8.3.36, 8.2.35**. Docker a suivi en moins de 24 h sur ses images officielles et durcies. Pour une équipe plateforme, la leçon est dans le délai : entre la publication upstream et le rebuild de vos images applicatives, il y a votre pipeline. C'est exactement le scénario où un `FROM php:8.4-apache` non daté vous sauve, et où une image épinglée à la main vous coûte une RCE.

### GitHub : le secret scanning sort des formats connus

Trois annonces qui dessinent une stratégie, pas trois features isolées.

**Push protection au-delà des motifs prédéfinis** (28 octobre, preview publique). Jusqu'ici, la protection reposait sur des formats connus — un `ghp_…` est reconnaissable, un secret maison ne l'est pas. GitHub déploie un **classifieur entraîné à évaluer l'usage du secret dans le code environnant**, développé avec Microsoft Applied Sciences, capable de bloquer un secret **sans format reconnaissable**. Résultats annoncés : **plus du double de pushes interceptés**, avec une précision comparable aux détecteurs fournis par les émetteurs partenaires. À savoir avant d'activer : le classifieur est **off par défaut**, il exige que *AI-detected secrets* **et** *push protection* soient déjà actifs, et **il consomme des AI credits** (facturation dès l'opt-in, alors que les alertes issues du scan post-push restent incluses dans GHSP/GHAS). Les workflows de bypass existants s'appliquent — et GitHub précise que **les agents doivent obtenir une autorisation avant de contourner un blocage**.

**Priorisation Dependabot par analyse de reachability** (28 octobre) : une alerte n'est plus traitée à égalité avec les autres ; on remonte celles dont le code vulnérable est réellement atteignable.

**AI Scan for pull requests en GA** (15 octobre) et **code scanning pour applications IA en preview** (28 octobre), plus un **package firewall en preview** (22 octobre) et la conformité de licences open source en GA (16 octobre). Sur une même période, sept publications touchent la supply chain : ce n'est plus un module, c'est un axe produit.

> **Analyse :** ✅ Très impactant (push protection par classifieur) : c'est la première réponse crédible aux secrets « maison » — mais le coût en crédits IA doit être chiffré avant activation à l'échelle de l'orga. ✅ Impactant (reachability Dependabot) : moins de bruit, donc plus de correctifs réellement appliqués. 👀 À surveiller (package firewall) : très prometteur, encore en preview.

## 🧭 Conseils & bonnes pratiques

**1. Traitez le trust store comme un artefact de build, pas comme un détail d'OS.** L'incident eMudhra a montré que trois couches doivent être alignées : le paquet système, le runtime compilé (Go, Node, Python/certifi), et **le bundle embarqué dans vos images**. Une image construite il y a six mois ne bénéficiera d'aucun patch hôte. Ajoutez un test qui échoue si l'âge du `ca-certificates` de l'image dépasse votre SLA.

**2. Verrouillez les dépendances de pipeline, mais relisez-les.** Un lockfile dit *ce qui s'exécute*, pas *si c'est sûr*. La bonne séquence : lockfile + Dependabot + revue humaine sur les montées d'action, et rien d'autre. Un lockfile sans revue fige aussi une compromission.

**3. Un dépôt Git n'est pas une frontière de sécurité.** Argo CD l'a démontré de la façon la plus directe : qui peut écrire dans le dépôt d'une Application influence ce que le controller crée, avec ses credentials. Signez les commits, imposez la revue sur les dépôts d'Applications, et restreignez les droits de destination des AppProjects au strict nécessaire — c'est la seule défense en profondeur qui reste quand une autorisation est contournée.

**4. Annoncez l'ordre de migration Kubernetes maintenant.** Trois échéances se télescopent : **1.34 est EOL**, **`failCgroupV1` bloque le kubelet en 1.35+**, et **1.38 arrive le 16 décembre** en poussant 1.35 vers sa fin de vie (février 2027). L'ordre correct est : cgroup v2 d'abord (c'est un prérequis de nœud), montée de version ensuite. L'inverse vous laisse avec des nœuds qui ne redémarrent pas.

**5. Ne confondez pas « corrigé » et « protégé » sur les CA.** Révoquer un certificat intermédiaire compromis protège ceux qui vérifient la révocation. Pour tous les autres, il faut retirer la confiance **et réémettre les feuilles**. Tant que vous ne savez pas quels certificats de votre inventaire chaînent vers ces intermédiaires, vous ne savez pas si vous êtes exposé.

**6. Mettez à jour les allowlists réseau avant les runners.** Le passage d'Actions à un pool multi-cloud est progressif et silencieux : pas de changement de YAML, pas d'erreur de configuration, juste des authentifications qui échouent quand un job tombe sur une nouvelle plage IP. Ajoutez toutes les plages Actions publiées à vos allowlists et à vos politiques Entra Conditional Access.

**7. Mesurez ce que coûtent les fonctions « IA » avant de les activer.** Push protection par classifieur consomme des crédits IA ; les agents de code review aussi. Une activation à l'échelle de l'organisation sans chiffrage est une ligne de facture, pas une amélioration de sécurité. Activez sur les dépôts exposés d'abord, mesurez, étendez.

## 🎯 Mise en perspective : impact sur la roadmap DevOps

Trois arbitrages pour les prochaines semaines.

**Ce mois-ci, la priorité n'est pas la nouveauté, c'est le patch.** GitLab CVSS 10.0, Argo CD 4 × 9.9, PHP2Shell, eMudhra + Go : quatre chantiers qui ont tous une échéance courte et une conséquence directe. Si votre backlog de plateforme doit accueillir une seule ligne en novembre, c'est celle-là : **inventaire des versions GitLab / Argo CD / PHP / runtimes Go, avec un propriétaire par ligne**. La bonne nouvelle est que ces correctifs sont tous disponibles — la mauvaise est que trois d'entre eux exigent plus qu'un `apt upgrade` (Runner et AI Gateway chez GitLab, rebuild d'images pour PHP et pour les trust stores).

**Ensuite, deux migrations à séquencer.** Kubernetes d'abord : **cgroup v2** sur les nœuds, puis montée en 1.35+ (1.34 est EOL, `failCgroupV1` bloque par défaut), avant que la 1.38 ne pousse 1.35 vers sa sortie en février 2027. Argo CD ensuite : sortir de la 2.x/3.0-3.2, qui ne recevront **aucun** correctif, et viser 3.5/3.6 sachant que la 3.3 sort du support le 3 novembre.

**Enfin, la vraie transformation est plus lente et plus rentable : rendre le pipeline prouvable.** Lockfiles Actions pour figer ce qui s'exécute, Terraform Policy pour évaluer le réel et pas seulement le plan, Secrets Manager pour que les secrets suivent les permissions, et un trust store testé comme un artefact. C'est moins visible qu'un agent qui rédige des PR, mais c'est ce qui fait la différence le jour où une CA tombe, où un tag bouge, ou où un hook `PostDelete` atterrit dans un dépôt.

*Prochaine veille : novembre 2026 — avec KubeCon NA, la GA d'Argo CD 3.6 et le code freeze de la 1.38.*
