# Veille A2A — Octobre 2026

> **Période couverte :** 1er → 31 octobre 2026. Rédigé le 01/11/2026.
> Protocole **Agent2Agent (A2A)**, standard ouvert d'interopérabilité entre agents IA, projet hébergé de l'**Agentic AI Foundation (AAIF)** / Linux Foundation depuis le 17 août 2026. **Spec stable : v1.0.1 (28 mai 2026)** — inchangée.

---

## 📌 Synthèse générale

Octobre 2026 est le mois où la **facture est arrivée**. Pas côté spec — elle n'a pas bougé d'un octet depuis mai — mais côté implémentations. En **48 heures (20-21 octobre)**, six CVE ont été publiées : **cinq dans le SDK Java** (`a2a-java`), toutes sur le même chemin — *push notifications, autorisation de tâche, gestion des credentials* — et **une dans le SDK Rust**. Quatre des cinq failles Java permettent à un **appelant non authentifié** d'obtenir quelque chose qu'il ne devrait pas : lire les tâches d'autrui (CVSS **7,5**, *fail-open* par défaut sur `InMemoryTaskStore`), faire émettre des requêtes HTTP au serveur vers son réseau interne (SSRF 5,8), ou récupérer des tokens de webhook écrits en clair dans les logs (CWE-532). Point contre-intuitif : **les correctifs étaient déjà livrés le 27 août** dans `1.3.0.Final`. Ceux qui sont restés en 1.2.x ont donc été exposés **huit semaines sans avis public** — et ceux qui ont migré en 1.3.x étaient patchés sans le savoir. La leçon du mois n'est pas « A2A est troué », c'est : **la spec est stable, les SDK ne le sont pas, et votre SBOM est votre vraie surface d'attaque.**

Le deuxième fait marquant est une **mesure**. Après deux ans de promesses sur l'interopérabilité, trois études indépendantes ont enfin chiffré le **coût d'un saut** entre agents. Résultat convergent et désagréable : le protocole n'est pas le problème, mais il a un prix. Une question posée en message streamé revient en **10,6 s pour 0,09 $** ; la même posée comme tâche persistante prend **153,6 s et coûte 1,28 $** (63 exécutions réelles). Délégrer à un agent distant coûte **6× le prix d'un appel d'outil MCP** — non pas à cause du réseau, mais parce que le pair est un agent : il raisonne, donc il refacture une inférence. Et **le handshake A2A est déjà le moins coûteux du marché** (1 aller-retour, 61 ms à 50 ms de RTT, contre 3 allers-retours et 230 ms pour MCP) : l'avantage est réel, mais il est écrasé par le coût du modèle en bout de chaîne. Bench arXiv du 2 octobre : NLIP est 4 à 9,6× plus rapide que le SDK A2A sur la coordination légère, mais **quasi parité en bout-en-bout** — c'est-à-dire que le choix de protocole se joue presque entièrement sur la latence de connexion, donc sur le pooling.

Troisième fil : **la gouvernance avance, la découverte recule**. AGNTCon + MCPCon North America (San Jose, 22-23 octobre) a battu des records — **4 300 inscriptions, 1 500 organisations**, AAIF passe à **10 projets hébergés** et **305 membres** — mais n'a apporté **ni release A2A, ni effort de découverte** repris par la fondation. La proposition **Agent Registry** ([discussion #741](https://github.com/a2aproject/A2A/discussions/741), 103 commentaires, 68 participants) a été **fermée** et redirigée vers AI Catalog / ARD, avec **au moins cinq implémentations incompatibles** déjà en production. Pendant ce temps, **Meta et Sierra publient le Personal Agent Protocol** (6 octobre, brouillon « Poppy » le 9, `/.well-known/poppy.json`, OAuth par utilisateur, 41 partenaires) et **Decagon lance PACT**. Traduction : la couche **identité-commerce** des agents est en train de se standardiser **à côté** d'A2A, pas dedans. A2A reste le transport d'exécution ; il n'est plus le lieu où se décide qui a le droit de parler à qui.

### 🧪 ACTS : la conformité sort enfin du « oui, ça se parle »

Le projet a séparé deux questions qui étaient confondues dans le TCK/ITK :

| Suite | Question posée | Dépôt |
|---|---|---|
| **ITK** (interoperability) | *Ces SDK peuvent-ils se parler, dans les deux sens, sur chaque transport ?* | [`a2aproject/a2a-itk`](https://github.com/a2aproject/a2a-itk) |
| **ACTS** (conformance) | *Ce SDK, seul, fait-il ce que la spec dit ?* | même dépôt, dossier `conformance/` |

ACTS est un **format de tests YAML** + un **corpus maintenu dans le dépôt A2A**. État au 31 octobre : **113 tests dans 14 fichiers** (+ manifeste), répartis en **101 tests sur JSON-RPC, 88 sur gRPC, 94 sur REST**, chaque test étiqueté `must` / `should` / `may` (RFC 2119). Les six SDK exécutent la suite en PR et en nightly, via le même lanceur d'agents.

Le détail qui compte — et qu'il faut lire avant de citer un score :

- Le corpus est épinglé à un commit de la branche `conformance-spec-adjustments` (**PR #2227**, elle-même ciblant la branche de **#1882** où la spécification ACTS est proposée). **Ni l'une ni l'autre n'est mergée dans `main`.** Le `1.0` dans `acts_version` est le numéro du **brouillon**.
- Dans les six dépôts, l'étape ACTS est en **`continue-on-error: true`** : un échec `must` **ne bloque aucun merge**. Le gate réel reste la traversée ITK. Le commentaire du workflow dit explicitement de retirer la ligne pour rendre ACTS obligatoire — « la ligne date de quand aucun SDK n'était conforme ».
- Le SDK .NET déclare `pushNotifications: false` : les tests de push y sont **skippés**, pas échoués. Un score parfait .NET ne dit donc rien sur cette zone.
- Un SDK **indépendant** (`a2a-rust`, projet non officiel) publie ses rapports ACTS : **JSON-RPC 101/101, gRPC 88/88, REST 94/94**, mesurés le **8 octobre** contre `a2a-itk` commit `82458ce`. C'est, à notre connaissance, le premier relevé public de conformité complète sur les trois bindings.

```yaml
# acts.yaml — extrait du workflow PR d'un SDK (a2a-itk/docs/conformance/04_ci.md)
on:
  pull_request:
    paths: ['src/**', 'acts/**', '.github/workflows/acts.yaml']
steps:
  - name: Run ACTS Conformance Suite
    continue-on-error: true      # ← à retirer pour gatér le merge
    run: bash run_itk.sh
    working-directory: itk
```

> 👀 **Lecture pratique** : ACTS est la meilleure chose arrivée à l'écosystème depuis la v1.0 — il transforme « supporte A2A » en **affirmations vérifiables**. Mais tant que (a) le corpus vit sur une branche non mergée et (b) le job est consultatif, un badge « conforme ACTS » en octobre 2026 est **une photo datée d'un brouillon**, pas une certification.

### 🗂️ Registre d'agents : la discussion fermée, le vide occupé par d'autres

La proposition [**#741**](https://github.com/a2aproject/A2A/discussions/741) (juin 2025, `kthota-g`) — catalogue d'agents, entitlements OAuth, `/agents/public`, `/agents/entitled`, `/agents/search` — est **close**. La convergence communautaire s'était faite sur une architecture *Core + Extensions* (Agent Card / Publication Record / Trust-Authorization Overlay ; search, resolve, snapshot), sans aboutir à une spec ratifiée. En août, le mainteneur avait redirigé vers **AI Catalog** et **ARD** comme chemin de découverte officiel — deux standards qui ont eux-mêmes leur ratification devant eux.

Conséquence chiffrée : **au moins cinq implémentations** de registre tournent avec des API incompatibles (Apicurio Registry, deux dépôts `a2a-registry` communautaires, une proposition d'intégration Quarkus LangChain4j). Carles Arnal (Apicurio) l'avait annoncé dès mai : *« la fenêtre d'interopérabilité se referme — plus on attend, plus l'alignement devient difficile. »* Octobre n'a rien réglé ; [Forkast](https://forkast.news/three-agent-specs-promised-for-october-remain-unshipped-the-vendor-extensions-filling-the-vacuum-are-fragmenting-the-stack/) liste d'ailleurs trois specs attendues en octobre et non livrées : PAP v0.1, la GA de Gemini agent, et le registre A2A.

### ⌨️ Le CLI devient un vrai outil d'exploitation

Le billet officiel du 1er octobre ([a2a-protocol.org](https://a2a-protocol.org/latest/blog/2026/10/01/introducing-a2a-cli/)) explique le trou que comble `a2a` : **la plupart des choses ne sont pas des agents**. Un script, un job cron, une étape de build, un harnais de code ne peuvent pas découvrir une carte, envoyer un message et suivre une tâche. Et les CLI communautaires avaient divergé (noms de commandes, flags, formes de sortie). Le CLI officiel est **bâti sur le CLI du SDK Go** et parle **A2A v1.0**.

```bash
# Découvrir, interroger, streamer — trois commandes
a2a card get https://agent.example.com
a2a send -a https://agent.example.com "Hello, what can you do?"
a2a send -a https://agent.example.com --stream "Summarize this document"

# Transformer N'IMPORTE QUEL script stdin/stdout en serveur A2A
a2a server --exec "python3 -u mon_agent.py" --chunk=$'\n' --port 8080
```

Le mode `--exec` mérite qu'on s'y arrête : le message arrive sur **stdin**, tout ce qui sort sur **stdout** devient la réponse, `exit 0` = `COMPLETED`, non-zéro = `FAILED`, `stderr` est journalisé et rattaché à l'échec. **C'est tout le contrat.** C'est un chemin de migration très bon marché pour du code existant — et un rappel que la valeur d'A2A n'est pas dans la sémantique des tâches mais dans **l'uniformité de la surface**. (`--echo` et `--exec` sont explicitement marqués *pas pour la production*.)

### 🟢 Go 2.7.0 : la rigueur de négociation arrive

Trois changements qui ont l'air mineurs et qui ne le sont pas : **rejet des `A2A-Version` non supportées** (#457), **`application/a2a+json` avec négociation `Accept`** (#465, avec repli correct quand `Accept` vaut `*/*` ou est absent), et **validation des modes d'entrée** (#456). Ajoutez le rejet des octets après le corps JSON et le mapping des erreurs HTTP non-A2A par code de statut : le SDK Go devient le plus strict de la famille sur les **bords** du protocole — exactement là où les interopérabilités échouent en pratique.

### 🟦 .NET : le dernier SDK non-GA se met à niveau

`preview3` (14 octobre) apporte le **binding gRPC complet** — client et serveur ASP.NET Core — soit la parité de transports avec Python/Go/Java. S'y ajoutent le **cache HTTP de l'Agent Card** (le champ était spécifié, rarement implémenté), l'aplatissement des `TaskPushNotificationConfig` conformes v1, et l'application de l'**état terminal premier-persisté sous verrou de tâche** (#401), qui corrige une classe de courses où deux événements terminaux concurrents laissaient une tâche incohérente. Reste que .NET est, à fin octobre, **le seul SDK officiel sans version stable** — plus d'un an après la v1.0 de la spec.

### ☕ Java : rien à signaler côté features, tout côté sécurité

`1.4.0.Final` date du **28 septembre** (SSE `SSEParserConfig` avec limite de ligne portée à 1 Mo, ordre des push notifications par tâche, résolution paresseuse de l'Agent Card, multi-tenant `@PublicAgentCard`). Octobre n'a publié **aucune** version : le mois a été consommé par la divulgation des cinq CVE ci-dessous.

**Ce que ces six CVE disent ensemble** — et c'est plus intéressant que chacune prise isolément :

1. **La spec n'est pas le problème.** Aucune de ces failles n'est une faille de protocole : toutes sont des **oublis d'implémentation** sur des champs que la spec définit (URL de push, nom d'en-tête, portée de tâche). Un audit ACTS ne les aurait pas toutes trouvées — elles vivent dans le code de transport et de store, pas dans la sémantique des messages.
2. **Le push notification est le talon d'Achille.** Quatre des six passent par là. C'est logique : c'est le seul endroit du protocole où **un pair fournit une URL que votre serveur va appeler** — donc la seule surface SSRF native d'A2A. Si vous n'utilisez pas les push notifications, **désactivez-les** ; c'est le seul contrôle qui supprime 2/3 de ce risque d'un coup.
3. **Le `fail-open` par défaut est la vraie faute de conception.** Une autorisation qui devient permissive quand on oublie de la configurer est un piège à grande échelle, parce que l'oubli est le cas nominal d'un POC promu en production. `a2a-java` a corrigé en rendant le défaut *fail-closed* (#1095) — c'est le bon choix, mais c'est un **breaking change silencieux** pour quiconque comptait sur le laisser-faire.
4. **Le délai de divulgation est le problème de gouvernance.** Correctif le 27 août, CVE le 20 octobre. Huit semaines pendant lesquelles les utilisateurs de 1.2.x n'avaient **aucun signal**. Pour un protocole qui se veut « enterprise-ready », la cadence de divulgation compte autant que la cadence de release.
5. **La convergence inter-SDK existe, mais par accident.** Le même mois, `a2a-python` 1.2.3 livrait de son côté « **reject push URLs in shared address space** » (#1326) — sans CVE, sans coordination annoncée. Les mainteneurs traitent le même risque en parallèle ; ils ne le traitent pas ensemble.

```properties
# Durcissement push côté a2a-java ≥ 1.3.0 (défauts après correctif)
a2a.push-notification.url.allowed-schemes=https
a2a.push-notification.url.allow-private-network-targets=false
# + egress proxy devant le serveur, qui refuse les redirections vers RFC1918
```

### 🔬 « Protocol pivoting » : la confiance se perd à la traduction

[Ars Technica, 5 octobre](https://arstechnica.com/security/2026/10/vulnerability-in-agents-from-google-and-others-exposes-structural-flaw-in-mcp/) — le chercheur indépendant **Syed Anas Mohiuddin** a reproduit une classe d'attaque sur **cinq organisations** (Google, JP Morgan Chase, Weaviate, Rapid7, la DINUM française, l'État fédéral américain). Le principe : l'attaquant entre par un protocole (MCP), l'agent relaie l'instruction à un pair **via un autre protocole** (A2A, ANP), et le second agent exécute **parce qu'il fait confiance au premier**. Il nomme cela le **protocol pivoting** ; Markus Vervier (X41 D-Sec) objecte qu'il s'agit d'une sous-classe d'**injection de prompt indirecte** — le débat sémantique importe peu, la citation de Douglas McKee (Rapid7) résume le fond : *« chaque protocole a été construit en supposant qu'il vivait seul ; chacun surveille sa porte d'entrée et personne ne regarde le couloir. »* Les CVE vont de **2,7** (Rapid7) à **8,0** (boîte à outils MCP `googleapis/mcp-toolbox`, SSRF par redirection, corrigée par allow-list d'IP au démarrage). Le lien avec A2A est direct : **A2A est précisément le protocole qui transporte une délégation d'un domaine de confiance à un autre** — donc le maillon où l'autorisation se perd si elle n'est pas re-vérifiée à l'arrivée.

Cinq briques : découverte par `/.well-known/poppy.json`, sessions, **sign-in OAuth**, persistance cross-canal, exécution de tâches sur site/API/agent. 6 partenaires au lancement, **35 de plus le 9** (OpenAI, Visa, Mastercard, Okta, Cloudflare) — **Anthropic absent**. **PACT** (Decagon, 6 oct) sur le consentement et la détection d'agents personnels. À noter pour la comparaison : PAP vise **le commerce** (un humain, un agent, une entreprise) là où A2A vise **la collaboration agent-agent** — mais les deux ont besoin de la même primitive (identité + consentement), et c'est PAP qui l'a publiée en premier.

### Ce que ces chiffres disent (et ce qu'ils ne disent pas)

- **Le coût d'un saut, c'est une inférence.** Les 6× de l'étude AWS ne viennent pas du réseau (`us-central1 → us-east-1`, quelques dizaines de ms) mais du fait que **le pair est un agent** : il planifie, appelle un outil, rédige. Déléguer, c'est acheter de l'indépendance au prix d'un tour de modèle. Corollaire : un saut supplémentaire dans une chaîne n'est pas « un peu plus de latence », c'est **un modèle de plus sur le chemin critique**.
- **La forme de l'appel vaut plus que le protocole.** 10,6 s / 0,09 $ en message streamé contre 153,6 s / 1,28 $ en tâche persistante, pour la même question. Les tâches rapportent par lots de 30 à 90 s. Conclusion opérationnelle de l'auteur : **une question appelle un message ; une investigation appelle une tâche** (parce que la tâche, elle, donne `cancel`, la déduplication et un lien vers la console).
- **La durabilité n'est pas gratuite et l'indurabilité est dangereuse.** Store en mémoire : au redémarrage, la tâche **disparaît** (`TaskNotFoundError`). Store SQLite : la tâche survit mais peut rester **`WORKING` pour toujours** si le process meurt en cours de travail — le SDK ne la marque pas `FAILED`, **c'est à vous d'écrire le reaper**. `a2a-python` 1.3.0 a précisément ajouté la libération des tâches parquées après timeout : la primitive existe désormais, encore faut-il la configurer.
- **Les tests d'interopérabilité qui ne quittent pas le laptop testent des mocks.** Sur les six défauts trouvés en inversant maître/esclave entre deux clouds, cinq n'étaient visibles qu'en déployé : versions de protocole, extras de dépendances, fédération d'identité, propagation d'en-têtes, formes d'URL.
- **Et le meilleur argument pour A2A vient d'un article qui le critique** : « A2A est pour les étrangers ». Là où vous ne contrôlez pas l'appelant (autre département, autre vendor, plateforme type Gemini Enterprise ou Copilot Studio), le contrat standard se rentabilise immédiatement. À l'intérieur de votre propre flotte, un sous-agent et un bus de messages coûtent **20× moins** en latence et **50 Mo de moins** en image.

## 🎯 Conseils / recommandations concrètes

1. **Faites l'inventaire SBOM de vos SDK A2A cette semaine.** Seuils : `a2a-java` **≥ 1.3.0.Final** (et **1.3.2.Final** si vous avez un client Android), `a2a-rs` **> 0.4.3**, `a2a-python` **≥ 1.2.3**, `a2a-go` **≥ 2.7.0**. Le CVE le plus grave (7,5) est un défaut d'autorisation : il ne se voit pas dans les tests fonctionnels.
2. **Désactivez les push notifications si vous ne les utilisez pas.** Quatre des six CVE du mois passent par ce chemin. Si vous en avez besoin : allow-list de schémas (`https` uniquement), refus des réseaux privés et des plages link-local/métadonnées cloud, **`followRedirects=false`**, épinglage DNS à la résolution, et proxy d'egress devant le serveur.
3. **Auditez vos logs.** CVE-2026-111762 écrit les tokens de webhook en clair au niveau `SEVERE`. Cherchez les corps JSON de `pushNotificationConfig` dans votre agrégateur, purgez, et ajoutez un scrubber sur les champs `token` / `credentials` avant de considérer le sujet clos.
4. **Rendez l'autorisation explicitement obligatoire.** Fournissez un `TaskAuthorizationProvider` (ou l'équivalent) **même quand vous croyez ne pas en avoir besoin**, et ajoutez un test qui doit échouer : `getTask` sans authentification ⇒ `401`, pas `200`. Un défaut permissif ne se voit qu'en le testant à l'envers.
5. **Ne construisez pas sur le registre d'agents.** Cinq implémentations incompatibles, pas de spec ratifiée, discussion fermée. Découverte = cartes + configuration explicite (ou un registre **traité comme pont temporaire**, jamais comme fondation). Gardez la logique d'agent indépendante de l'implémentation du registre.
6. **Gatez la CI sur ACTS (`must`) et gardez ITK pour l'interop.** ITK répond « peuvent-ils se parler », ACTS « fait-il ce que la spec dit ». Aujourd'hui, dans les dépôts officiels, **seul ITK bloque un merge** — reproduisez ACTS chez vous avec `--require-conformant`.
7. **Choisissez la forme de l'appel selon la nature de la question.** Message streamé pour une question (ordre de grandeur : 10 s / 0,09 $) ; tâche persistante seulement si vous avez besoin de `cancel`, de déduplication ou d'un suivi multi-jours (ordre de grandeur : 2,5 min / 1,28 $).
8. **Traitez la durabilité des tâches comme un sujet d'exploitation, pas de configuration.** Store durable + **reaper** pour les tâches `WORKING` orphelines + alerte sur les tâches non terminales au-delà de N minutes. Un store SQLite par défaut multiplie la latence par 15 : mesurez avant de basculer.
9. **Négociez explicitement la version.** Envoyez `A2A-Version` (son absence vaut **0.3**, pas « la dernière »), publiez **1.0 et 0.3** en interfaces séparées tant que votre parc n'a pas migré, et testez le comportement d'un serveur qui rejette une version inconnue (le SDK Go 2.7.0 le fait désormais).
10. **Instrumentez chaque saut en dollars, pas seulement en millisecondes.** Nom de l'agent appelé, `protocolVersion`, `taskId`/`contextId`, tokens consommés par les deux côtés, coût estimé. Sans cette trace, vous ne saurez jamais si votre chaîne de trois agents est rentable ou si elle consomme 80 % du budget pour 5 % de la valeur.

## ⚖️ Analyse critique

- ✅ **La conformité devient mesurable.** ACTS (113 tests, 3 bindings, niveaux RFC 2119) + ITK + rapports publics d'un SDK indépendant : c'est la première fois qu'on peut dire « conforme » avec une pièce jointe. C'est le vrai progrès d'octobre, même s'il est invisible dans les release notes.
- ✅ **Les SDK corrigent vite et en profondeur.** Cinq avis publiés le même jour, correctifs déjà livrés, défauts passés en *fail-closed*, validation des versions inconnues, rejet des URLs push privées côté Python : la dette de sécurité de l'écosystème est en train d'être payée, pas repoussée.
- ✅ **Le coût d'un saut est enfin documenté.** Quatre études indépendantes, quatre méthodologies, un même ordre de grandeur. Un architecte peut maintenant arbitrer avec des chiffres au lieu d'intuitions.
- 🔴 **Le délai correctif → divulgation (8 semaines) est inacceptable pour un standard « enterprise ».** Et il n'existe aucun mécanisme de notification côté projet : ni advisory GitHub agrégé, ni fil dédié. Vous l'apprenez par votre scanner, souvent après.
- 🔴 **La découverte est un échec de standardisation.** Un protocole dont le registre n'existe pas encore oblige chaque entreprise à réinventer son catalogue — exactement le problème qu'A2A devait supprimer. Pendant ce temps, PAP publie son `/.well-known/poppy.json` en deux jours.
- 🔴 **Concentration du risque sur un SDK.** Les cinq CVE Java concernent le même sous-système (`server-common` : push, store, auth). Un écosystème à six SDK où un seul concentre les failles critiques n'est pas encore diversifié : il est **dépendant**.
- ⚪ **Adoption profonde toujours hétérogène.** .NET reste en preview, JS silencieux en octobre, Java sans release fonctionnelle. « Supporte A2A » couvre toujours un spectre qui va de l'endpoint qui répond 200 au SDK qui passe 101 tests de conformité.
- 👀 **À surveiller** : merge (ou abandon) de la PR #2227 / #1882 (ACTS) ; passage d'ACTS en gate obligatoire dans les six dépôts ; sortie de v1.1 ; arrivée de l'identité (RFC 9421, A2A-IDF) ; convergence ou guerre des trois couches d'identité (PAP/Poppy, PACT, A2A-IDF) ; sortie de la preview .NET ; et la question qui fâche — **combien de nouvelles CVE A2A en novembre ?**

## 🔭 Mise en perspective

Octobre 2026 a tué deux illusions.

La première : **« la spec est stable, donc c'est sûr »**. La v1.0.1 n'a pas changé d'une ligne et, en deux jours, six failles ont été publiées — toutes dans les implémentations, toutes sur des champs que la spec définit pourtant clairement. Pour une équipe qui évalue A2A, cela déplace la question : le risque n'est pas « le protocole est-il mûr ? » mais **« quel SDK, en quelle version, avec quels défauts par défaut ? »** Le contrat est stable ; le code qui l'implémente ne l'est pas encore. C'est une différence de nature pour les processus d'achat et de gouvernance : on n'évalue plus un standard, on évalue une chaîne d'approvisionnement.

La seconde : **« l'interopérabilité est un problème de protocole »**. Les benchmarks d'octobre montrent qu'à 6,4 ms de handshake, le transport n'est plus le facteur limitant : ce qui coûte, c'est **le raisonnement du pair** (6× un appel d'outil) et **la forme de l'appel** (×14 entre un message et une tâche). Autrement dit, l'architecture multi-agents est désormais une **question de budget et de topologie**, pas de format de message. La conséquence pratique est contre-intuitive : **moins de sauts, mieux placés**, battent une maille fine de spécialistes — et le meilleur usage d'A2A est la frontière organisationnelle, pas l'intérieur de son propre système.

Reste la troisième histoire, plus lente : **où se décide l'identité**. A2A a passé octobre à corriger des contrôles d'accès (portée de tâche, en-tête, URL de push) — c'est-à-dire à rafistoler localement une couche qui n'est pas encore standardisée chez lui. Au même moment, Meta/Sierra publient en trois jours un protocole d'identité et de consentement avec 41 partenaires, Decagon en publie un autre, et la fondation qui héberge A2A annonce dix projets sans reprendre le chantier de découverte. Le risque n'est pas qu'A2A meure — il est utilisé en production chez 150+ organisations et dans trois hyperscalers. Le risque est qu'il devienne **un excellent tuyau sous une couche d'identité qui ne lui appartient pas**. Ce n'est pas forcément un problème ; c'est un changement de position dans la pile, et il faut le savoir avant de dimensionner ses investissements sur A2A.
