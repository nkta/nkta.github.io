## 📌 Synthèse générale

Le fait marquant du mois est **institutionnel et non technique** : le protocole A2A a officiellement rejoint l'**Agentic AI Foundation (AAIF)**, la fondation « spécialisée agents » dirigée par la Linux Foundation, le **17 août 2026**. Annoncée en exclusivité par Axios puis confirmée par le blog officiel [a2a-protocol.org](https://a2a-protocol.org/latest/blog/2026/08/27/a-new-chapter-for-a2a-joining-the-agentic-ai-foundation/) le **27 août**, la bascule place A2A aux côtés de ses « frères » déjà hébergés : **MCP, goose (Block), AGENTS.md (OpenAI) et agentgateway**. À retenir : **c'est la fondation d'accueil qui change, pas la gouvernance ni les mainteneurs**. Le standard reste indistinct de ses précédentes activités, mais la cohabitation MCP + A2A sous un même toit renforce le narratif « **MCP = intégration verticale** (agent → données/outils), **A2A = orchestration horizontale** (agent → agent) ».

Côté implémentations, le mois est marqué par une grosse vague de **durcissement sécurité** portée par l'écosystème. Le [A2A Java SDK](https://a2aproject.github.io/a2a-java/announces) est passé en deux releases rapprochées — **1.2.0.Final le 7 août** puis **1.3.0.Final le 27 août** — la seconde introduisant la **multi-tenant native**, un modèle d'autorisation **fail-closed par défaut** et **trois GHSA corrigées**. Dans le même temps, la spec elle-même **n'a pas bougé : v1.0.1 (28 mai 2026) reste la version stable courante**, ce qui confirme que la charge de l'interopérabilité s'est déplacée vers les SDK.

Enfin, la **sécurité** s'impose comme le vrai champ de bataille de 2026 : cartes d'agents signées, tokens OAuth/OIDC à scope par skill, anti-SSRF sur les webhooks push, et isolement strict entre tenants. Le tout adossé à une montée en maturité des **bonnes pratiques zero-trust** poussées par Google ([ADK](https://developers.googleblog.com/en/build-zero-trust-ai-agents-with-googles-agent-development-kit/), [Cloud Run](https://medium.com/google-cloud/implementing-zero-trust-a2a-with-adk-in-cloud-run-243aa4fb98ad)) et par des guides d'architecture dédiés.

## 🔌 Implémentations : servers / clients / hosts

### A2A Java SDK — deux releases en août

Le Java SDK est devenu **le fer de lance** du durcissement sécurité et multi-tenant en août 2026.

**1.3.0.Final (27 août 2026)** — *breaking changes* :
- 🏢 **Multi-tenancy** : un seul serveur sert plusieurs tenants avec des `AgentExecutor` et `AgentCard` propres. Deux nouveaux SPIs (`AgentExecutorRouter`, `AgentCardRouter`) + module CDI `a2a-java-extras-multitenancy`. Cartes publiques servies sous `/.well-known/{tenant}/agent-card.json` ; ID de tenant limités à `a-zA-Z0-9_.-`.
- 🔒 **Autorisation fail-closed par défaut**.
- 🛡️ **Vague de durcissement** (détail en section Sécurité).
- **AgentExecutor devient `@FunctionalInterface`** — les agents simples peuvent être des lambdas :

```java
AgentExecutor executor = (context, emitter) -> {
    emitter.text("Bonjour !");
    emitter.done();
};
```

```java
// Routage multi-tenant sans CDI
AgentExecutorRouter router = tenant ->
    executors.getOrDefault(tenant, defaultExecutor);

DefaultRequestHandler handler = DefaultRequestHandler.builder()
    .agentExecutorRouter(router)   // remplace .agentExecutor() en multi-tenant
    .taskStore(taskStore)
    .queueManager(queueManager)
    .build();
```

**1.2.0.Final (7 août 2026)** — *breaking changes* : comble les trous du SPI `TaskAuthorizationProvider` (introduit en 1.1.0 pour l'autorisation par utilisateur), ajoute la **gestion du cycle de vie des streams** et corrige des points de conformité.

### SDK Rust « a2a-rust »
- Protobuf-natif **gRPC** (transport `lf.a2a.v1.A2AService`), **WebSocket** authentifié (les 11 méthodes routées), **TLS first-class** (`tls-rustls` par défaut).
- Améliorations de conformité et de perf (streaming, `InMemoryTaskStore::list()` en O(log n), ~80 allocations de moins par `Task`).
- ⚠️ **Advisory de dépendance** : `rustls-webpki` 0.103.12 corrige **RUSTSEC-2026-0098** (GHSA-965h-392x-2mh5) — contraintes de nom d'URI acceptées à tort lors de la validation de chemin X.509. Atteint `a2a-protocol-client` **transitivement via `rustls`** quand `tls-rustls` est activé. *Mise à jour drop-in, aucun changement d'API.*

### Modèle de menace & bonnes pratiques (maturité 2026)
- **La task ID opaque ne doit pas devenir un « bearer credential »** : dans un serveur A2A multi-tenant, une `taskId` opaque ne doit pas permettre à un appelant de récupérer le travail, l'historique ou la config de callback d'un autre tenant. Les SDK l'ont compris (Go v2.4.0 : checks cross-tenant ; Java 1.1.0+ : `TaskAuthorizationProvider` par utilisateur).
- **Cartes d'agents signées** : `AgentCardSignature` (JWS RFC 7515) appliqué **après canonicalisation JSON** (RFC 8785). Garantie limitée à la confiance que l'on accorde à la clé → il faut établir que la clé appartient bien à l'organisation annoncée (concept clé, cf. Forbes).
- **Immédiat de sécurité** : ne pas mettre de secrets dans la carte ; préférer l'**Extended Agent Card** authentifiée (`GetExtendedAgentCard`); scoper les tokens OAuth par skill (`scope` → `skills[]`); court `exp`, `jti` cache pour anti-rejeu; **DPoP (RFC 9449)** ou **mTLS (RFC 8705)** pour les opérations à haut risque.
- **Menaces principales** : empoisonnement de contexte (description/skills de la carte), usurpation d'agent, **SSRF webhook**, rejeu de token, manipulation de paramètres.

### Gouvernance
- **EU AI Act** : la fondation publie un guide d'implémentation (AAIF, 2 août 2026) — risque, transparence, supervision, responsabilité dans la stack agentique. À intégrer dès la conception pour les agents traitant des PII ou des flux financiers.
- **Neutralité** : A2A est protégé de tout verrouillage fournisseur (gouvernance Linux Foundation / AAIF). En contrepartie, la **politique d'autorisation inter-organisations** reste explicitement à la charge de l'entreprise — le standard ne la standardise pas.

## ⚖️ Analyse critique

- ✅ **Maturité** : la spec est **stable (v1.0.1)**, la gouvernance est **neutre et désormais centralisée** avec MCP sous l'AAIF. 150+ organisations, supports cloud natif (GCP, AWS, Azure) et SaaS majeurs. Le mouvement AAIF réduit le risque de fragmentation et de dépendance à un seul fournisseur.
- ✅ **Sécurité en progrès** : la vague de durcissement (SSRF, fuite de credentials, fail-closed, multi-tenant) montre un écosystème qui prend au sérieux les menaces réelles — exactement ce qu'on attend d'un protocole inter-organisations.
- ⚪ **Limite structurelle** : la spec figée signifie que **l'interopérabilité est de facto définie par les SDK**, et on voit des implémentations diverger (canonicalisation des signatures, handlers legacy). Risque de « *qui se ressemble s'assemble* » entre les versions.
- ⚪ **Profondeur d'adoption hétérogène** : héberger un endpoint A2A ≠ supporter bindings, négociation de version, multi-tenant et cartes signées (Forbes). Les allégations de support des plateformes varient fortement.
- 👀 **Conformité à vérifier** avant adoption : quelle révision, quels bindings, la plateforme rejette-t-elle les cartes non signées, comment établit-elle la clé de l'organisation, isolement entre tenants, **traçabilité** (qui a audité quoi).
- 👀 **Coût de gouvernance** : la gouvernance consensuelle peut ralentir le rythme de release — à surveiller sous l'AAIF.
- 👀 **Concurrence d'espace** : Cisco AGNTCY (découverte/identité) chevauche partiellement A2A ; à suivre.

## 🎯 Conseils / recommandations concrètes

1. **Adopter une posture zero-trust dès le départ** : cartes signées (JWS/RFC 7515) obligatoires, tokens OAuth/OIDC à scope par skill, `jti` cache anti-rejeu, `exp` court. Ne mettre **jamais** de secret dans la carte.
2. **Isoler les tenants** : si vous servez plusieurs clients, passer à la multi-tenant (Java 1.3.0) et vérifier les **vérifications cross-tenant** sur les stores (taskId ≠ bearer credential).
3. **Sécuriser le chemin push** : les webhooks sont une surface SSRF — allow-list, validation du schéma, blocage des réseaux privés (y compris IPv4-mapped IPv6), et n'activer le stockage push que si nécessaire.
4. **Fixer la conformité côté plateforme** : exiger la version A2A supportée, les bindings, l'auto-négociation de version avec les clients plus anciens.
5. **Se préparer à l'EU AI Act** surtout si l'agent touche des PII ou des opérations financières (transparence, supervision humaine, auditabilité).
6. **Penser A2A comme un « agentic microservice »** : dissocier les agents, les scaler indépendamment, limiter la propagation de privilèges dans les chaînes de délégation (least-privilege).

## 🔭 Mise en perspective

Le rapprochement **A2A + MCP** sous une même fondation consacre l'architecture à **deux couches** : MCP (agent → outils/données, vertical) et A2A (agent → agent, horizontal). Cela réduit la peur de la fragmentation et incite les équipes à construire des stacks plus **modulaires et model-agnostiques**, avec la liberté de changer de fournisseur selon coût/performance/latence.

Pour la productivité, le bénéfice est net : **un agent peut être construit une fois et appelé par des dizaines d'agents** dans toute l'entreprise, sans réécrire d'intégrations ad hoc à chaque nouvelle paire. La contrepartie (zéro-trust, gouvernance, conformité) est désormais le vrai coût d'entrée — et c'est précisément là que l'écosystème concentre ses efforts en 2026.
