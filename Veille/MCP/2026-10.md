# Veille MCP — Octobre 2026

*Auteur : Nicolas Koudota — 1er novembre 2026*

*Période couverte : octobre 2026 (1 → 31)*

> Octobre est le mois où MCP a **cessé d'être un protocole pour devenir une plateforme**. Aucune nouvelle révision datée (la **2026-07-28** reste la référence), mais trois bascules structurelles : les serveurs de référence ont **changé de génération** (v1.0.0 « legacy » figée → v2.0.0 « modern era »), GitHub a lancé ses **connecteurs MCP vérifiés** (26 services, un compte, cinq surfaces Copilot), et le registre officiel est passé de **39 000 à 53 500 serveurs en 30 jours** (+42 %). En parallèle, la sécurité a livré son lot : **8 vulnérabilités** dans les serveurs de référence, **3 CVE** dans le SDK Python le même jour, un **bypass d'audience de jeton** dans les deux SDK, et une compromission d'autorité de certification (eMudhra) qui a forcé une release de sécurité hors cycle.

---

## 🔥 Les 4 faits marquants

- **La génération de serveurs bascule — et se sépare en deux lignes** 🔀 : le 11 octobre, `v1.0.0` clôt la lignée historique (« final legacy release »). Le 19, `v2.0.0` refactore **tous** les serveurs de référence pour la spec moderne, tout en continuant à répondre aux clients legacy. Six jours plus tard, `v2.1.0` corrige **huit vulnérabilités** dans trois serveurs. Trois releases majeures en dix-sept jours : la maintenance devient un travail à plein temps.
- **GitHub fait de MCP un produit, plus une config** 🐙 : le 28 octobre (GitHub Universe), les **serveurs MCP vérifiés par GitHub** passent en *public preview* — 26 services (Slack, Figma, Notion, Sentry, Linear, Atlassian Rovo, Cloudflare, Vercel, Work IQ). On se connecte **une fois**, et le connecteur fonctionne dans l'app Copilot, la CLI, VS Code, Copilot dans le cloud et GitHub Mobile. Ce n'est plus « trouvez un serveur, installez-le, gérez un secret » : c'est « choisissez un service, signez ». Le modèle de distribution du web (OAuth + annuaire) vient d'absorber MCP.
- **Le client rattrape la spec : Tasks + Elicitation en prod** ⏳ : le 22 octobre, David Soria Parra annonce en keynote (AGNTCon + MCPCon North America, San Jose) que Claude Code supporte les **MCP Tasks** ; le 23, Anthropic confirme dans la CLI **v2.1.304+** (public beta) — Tasks *et* Elicitations, y compris **une question posée depuis l'intérieur d'une tâche en cours**. C'est la première implémentation cliente réelle du motif « travail durable » que la 2026-07-28 a introduit via MRTR + extension Tasks.
- **La sécurité se déplace du code vers la chaîne de confiance** 🧨 : côté protocole, `CVE-2026-104850` (le serveur décide **quel** serveur d'autorisation reçoit vos credentials OAuth, CVSS 7.5) puis `CVE-2026-111771` (jeton accepté pour un **autre** service) ; côté IDE, `CVE-2026-103572` dans Copilot pour Visual Studio/SSMS (CVSS **8.8**, Patch Tuesday du 13) ; côté infrastructure, la compromission de **huit CA intermédiaires eMudhra** dont les clés privées étaient récupérables depuis les certificats publics — ce qui a forcé `servers v2.2.0` à rebaser sur Node 24.22.1+ et `certifi 2026.10.23`.

## 1. Spécification & gouvernance — la découverte devient protocolaire

### Aucune révision, mais le mois le plus « normatif » depuis juillet

Le projet n'a publié **aucune révision datée**. Ce qui a bougé a pris deux chemins : les SEPs de **process** (cycle de vie, calendrier) et un SEP de **découverte** qui touche tout le monde.

- **SEP-2127 — « MCP Server Cards : HTTP Server Discovery »** 🪪 · [commit de merge](https://github.com/modelcontextprotocol/modelcontextprotocol/commit/0a11bf68c7ec4473526ec15589f592afcd12d1e8)
  L'idée : publier une **carte de serveur** vérifiable à une URL `.well-known`, pour qu'un client (ou un registre, ou un gateway) puisse savoir *ce qu'un serveur propose, avec quelle révision, sous quelle politique* — **sans ouvrir de connexion MCP**. C'est la brique qui manquait à tout l'écosystème d'annuaires. Conséquence directe : un index peut cesser d'être un scraper de README et devenir un consommateur de métadonnées déclaratives. Le **Server Card Working Group** continue en parallèle sur les conventions `.well-known`.

- **SEP-3392 — Extension Lifecycle, Final** ♻️ · [commit](https://github.com/modelcontextprotocol/modelcontextprotocol/commit/a1e969d3b3d327ab31f2b41637b76c94b954b329)
  Un cycle de vie formel pour les extensions, avec une précision qui compte : **« no conformance requirement »**. Autrement dit, un SEP de process ne crée **pas** d'obligation de conformité pour les implémentations. C'est exactement le genre de distinction qui manquait quand Skills est passé Final en septembre : « Final » ≠ « tous les clients doivent l'implémenter ».

- **SEP-3398 — Release Cycle Updates** 📅 · [commit](https://github.com/modelcontextprotocol/modelcontextprotocol/commit/ccaf9102ec5eb656eab50ca8333ef49dcd259c26)
  Modification du calendrier de release. À surveiller : c'est ce texte qui décidera **quand** la prochaine révision datée tombe, et donc la fenêtre de migration des SDKs.

### Gouvernance : les groupes se réorganisent autour de l'asynchrone

| Groupe | Mouvement | Effet | Date |
|---|---|---|---|
| **Tasks and Events WG** | **Créé** | Reconnaît Tasks + événements serveur comme un domaine à part entière, pas un détail de `tools/call` | ~22 oct. |
| **Agents WG** | Converti en **Interest Group** | Le groupe ne produit plus de SEPs : il alimente la réflexion | ~22 oct. |
| **Governance WG** | Charte adoptée | Propriété formalisée du processus lui-même | ~14 oct. |
| **Primitive Grouping IG** | Renommé **Progressive Disclosure WG** | La roadmap « amélioration des primitives » a désormais un groupe nommé d'après sa solution | ~14 oct. |

Le signal est net : la roadmap du 22 août listait « découverte progressive » comme un objectif. Fin octobre, c'est un **working group avec un mandat**. La prolifération d'outils (un serveur à 100 outils fait payer tout le catalogue au modèle avant la première question) est passée de « problème connu » à « chantier financé ».

### Le détail qui a cassé des serveurs : le quickstart

Le guide TypeScript « Build an MCP server » câblait `server.connect(new StdioServerTransport())` — qui ne sert que les clients de l'ère `initialize`. Un serveur construit depuis cette page **échouait la négociation** face à un client 2026-07-28, et l'Inspector masquait le problème en restant en ère `legacy` par défaut. Le correctif impose le motif *factory* :

```ts
// ✅ Le motif recommandé pour la 2026-07-28 : une factory, servie par serveStdio
import { serveStdio } from "@modelcontextprotocol/server/stdio";

const createServer = () => {
  const server = new McpServer({ name: "mon-serveur", version: "1.0.0" });
  server.tool("ping", async () => ({ content: [{ type: "text", text: "pong" }] }));
  return server;
};

serveStdio(createServer);   // ← au lieu de server.connect(new StdioServerTransport())
```

> 👀 **Leçon transposable** : un exemple officiel faux est plus coûteux qu'une absence d'exemple. Des serveurs « conformes » ont été déployés en croyant l'être, et l'outil de debug (Inspector en mode `legacy`) a validé leur erreur pendant des semaines. **Testez toujours en ère moderne explicite.**

## 2. Implémentations — SDKs & serveurs

### Le mois du grand écart de génération

Trois releases majeures des serveurs de référence en dix-sept jours, avec une logique claire :

1. **v1.0.0 (11/10)** — on **ferme** proprement la lignée historique, avec les correctifs de sécurité accumulés. Fin de la maintenance.
2. **v2.0.0 (19/10)** — on **ouvre** la lignée moderne : tous les serveurs refaits pour la spec stateless, **mais** réponse correcte aux clients legacy (dual-era assumé).
3. **v2.1.0 (25/10) / v2.2.0 (28/10)** — on **paie** la dette : huit vulnérabilités, puis la crise CA.

Le détail de v2.0.0 côté Python mérite un arrêt, parce que c'est le genre de changement qui casse silencieusement des clients :

- Un outil inconnu renvoie désormais `-32602` (erreur JSON-RPC), **plus** un résultat `isError`. La spec l'exige ; beaucoup de clients legacy ne l'attendaient pas.
- Les serveurs `fetch`/`git`/`time` sont rebâtis sur `MCPServer` du SDK Python 2.x (donc `mcp>=2.3,<3`).
- `get_current_time` et `convert_time` déclarent un `outputSchema` et renvoient `structuredContent`.

### C# 2.0 : le stateless devient le défaut, le routage devient une affaire d'en-têtes

C'est la release la plus lisible du mois sur *comment* la 2026-07-28 change l'exploitation · [InfoQ, 26/10](https://www.infoq.com/news/2026/10/MCP-CSharp-SDK-Stateless) · [annonce .NET](https://devblogs.microsoft.com/dotnet/announcing-v20-of-the-official-mcp-csharp-sdk/)

```csharp
// Streamable HTTP : stateless par défaut (fin du handshake, fin de Mcp-Session-Id)
var options = new HttpServerTransportOptions { Stateless = true };  // défaut en 2.0

// Un paramètre d'outil devient un en-tête HTTP → routage sans lire le corps
[McpServerTool]
public string GetOrder([McpHeader("Region")] string region, string orderId) { ... }
// → Mcp-Param-Region: eu-west   (+ Mcp-Method: tools/call, Mcp-Name: get_order)
// Le corps reste autoritaire : un en-tête incohérent → erreur HeaderMismatch.
```

Et le remplacement du canal retour, qui est le vrai changement conceptuel :

```csharp
// Le serveur ne peut plus "demander" en cours d'appel (plus de session).
// Il rend la main avec une demande d'entrée + un état opaque.
throw new InputRequiredException(
    InputRequest.ForElicitation("Confirmer le déploiement en prod ?"),
    requestState: opaqueToken);
// Le client collecte la réponse et RÉ-ÉMET le call avec inputResponses.
// McpClient le fait automatiquement si des handlers sont enregistrés.
```

Trois points d'attention relevés par la communauté, qu'aucune annonce ne met en avant :

- `McpClient.ServerInfo` devient **nullable** en 2.3 (changement cassant) parce qu'un serveur peut **omettre** son identité dans `server/discover`. La note est explicite : **ne pas utiliser l'identité auto-déclarée pour une décision de sécurité.**
- `requestState` est un jeton opaque qui circule — un lecteur a demandé publiquement s'il est protégé contre la **falsification** et la **réutilisation** entre sessions. Sans réponse à ce jour. 👀
- En HTTP moderne, la réponse attend le **premier message de protocole** avant d'envoyer les en-têtes : un handler long et silencieux dépasse le timeout. Il faut émettre du progrès.

### TypeScript 2.4.0 : Skills arrive enfin côté SDK

Le support de SEP-2640 (passé Final en septembre) atterrit en code · [release 2.4.0](https://github.com/modelcontextprotocol/typescript-sdk/releases/tag/v2.4.0)

```ts
// Serveur : publier un dossier de skills
import { SkillsExtension, loadSkills } from "@modelcontextprotocol/server/ext/skills";
const skills = await loadSkills("./skills");
new SkillsExtension(skills).attach(server);   // @experimental
// → sert skills/list, skills/get, resources/directory/read, skill://{+path}

// Client : lister, lire, VÉRIFIER
import { SkillsClient } from "@modelcontextprotocol/client/ext/skills";
const c = new SkillsClient(connection);
for (const s of await c.list()) {           // skipInvalid:true → garde les valides
  await c.read(s);                          // taille + digest + frontmatter vérifiés
}                                           // SkillsVerificationError si mismatch
```

Détail de conception qui compte : sur 2026-07-28 **seulement**, le serveur envoie `ttlMs` et `cacheScope`, et `SkillsClient` les **exige**. Sur 2025-11-25, ces champs n'existent pas. Un client qui code en dur l'un des deux comportements casse sur l'autre ère.

### Deux ruptures de compatibilité à connaître

- **`x-mcp-header` sur un `number` est illégal** en 2026-07-28. Le SDK TS **rejette** l'outil au listing et répond `-32020` à l'appel ; le SDK Python lève `InvalidSignature` **à l'enregistrement** (avant, le serveur démarrait et le client *disparaissait* l'outil du listing en silence — le pire des cas). Utilisez `z.int()`.
- **`outputSchema` depuis `z.object(...).meta({ id })`** : sur une connexion 2025-11-25, le résultat n'est **plus** enveloppé dans `{ result }`. Lisez `structuredContent`, pas `structuredContent.result`.

## 3. Hôtes & adoption — MCP devient une fonctionnalité produit

### GitHub : 26 connecteurs, une connexion, cinq surfaces

· [changelog GitHub, 28/10](https://github.blog/changelog/2026-10-28-connect-your-tools-to-copilot-without-all-the-setup/) · [VS Code Wrapped / Universe](https://code.visualstudio.com/blogs/2026/10/28/vscode-wrapped/)

- **Serveurs MCP vérifiés par GitHub** (« connecteurs »), *public preview* sur **tous les plans Copilot**. Lancement avec 26 services : Slack, Figma, Notion, Sentry, Linear, Atlassian Rovo, Cloudflare, Vercel, Work IQ.
- **Connexion unique** : le connecteur établi dans un endroit fonctionne dans l'app Copilot, la CLI (`/mcp` → onglet *Connectors*), VS Code (Agents → Customizations), Copilot dans le cloud et GitHub Mobile. Copilot **maintient la session** en arrière-plan.
- Pas de serveur à trouver, rien à installer localement, **aucun credential à gérer**. Les connecteurs ne fonctionnent qu'avec le *harness* Copilot.
- Gouvernance : en Business/Enterprise, un admin doit activer `Editor preview features` ; si un **allowlist MCP** est en place, il faut y ajouter les serveurs vérifiés. Certains services exigent aussi une autorisation côté éditeur.

> 🔍 **Ce que ça change vraiment** : le problème n°1 de l'adoption MCP en entreprise n'était pas technique, c'était **la distribution et la confiance**. GitHub ne vend pas un protocole, il vend un annuaire *curé* avec OAuth géré. Corollaire pour un éditeur : être dans l'annuaire d'un hôte devient plus important que d'avoir un bon serveur. C'est la capture par le catalogue, exactement comme pour les app stores.

### VS Code 1.144 : MCP Apps entre dans l'éditeur

- Support **MCP Apps** (l'extension `io.modelcontextprotocol/ui`, stable depuis le 2026-01-26) — les serveurs peuvent rendre des UI interactives (graphiques, formulaires, lecteurs) **dans** la conversation.
- Les auteurs d'extensions peuvent exposer **des outils d'agent et des serveurs MCP via le Marketplace**.
- Les connecteurs Copilot (preview) apportent le contexte de Slack, Notion, Microsoft Learn « sans installer ni gérer un serveur MCP ».

### Claude Code : le premier client qui fait vraiment tourner Tasks

· [annonce Anthropic, 23/10](https://x.com/ClaudeDevs/status/2113698001889927608) · [docs Claude Code](https://code.claude.com/docs/en/mcp#mcp-tasks-for-server-authors) · [explication Upstash](https://upstash.com/blog/claude-code-mcp-tasks)

Le protocole d'échange, tel que Claude Code l'implémente :

```jsonc
// 1) Le client déclare l'extension dans le _meta de CHAQUE requête (plus de handshake)
{ "_meta": { "io.modelcontextprotocol/clientCapabilities":
    { "extensions": { "io.modelcontextprotocol/tasks": {} } } } }

// 2) Le serveur accepte le job et rend un handle au lieu d'un résultat
{ "resultType": "task",
  "taskId": "exp-2026-10-31-001",   // ≤128 ASCII imprimables, sans espace
  "status": "working",
  "createdAt": "2026-10-31T09:00:00Z",
  "lastUpdatedAt": "2026-10-31T09:00:00Z",
  "ttlMs": null,                     // null autorisé
  "pollIntervalMs": 2000 }

// 3) Le client interroge tasks/get ; en cas de besoin d'input → status "input_required"
//    → dialogue utilisateur → tasks/update avec la réponse
```

Les contraintes réelles, qui sont la vraie information :

- **Périmètre étroit** : CLI interactive, sessions Agent SDK, runs GitHub Actions. **Pas** l'extension VS Code, **pas** l'app desktop, **pas** les subagents, **pas** `claude -p` one-shot, **pas** Bedrock ni les fournisseurs qui ne récupèrent pas les feature flags.
- Le serveur doit parler **2026-07-28** ; forcer `MCP_SDK_GENERATION=v1` ou `MCP_PROTOCOL_NEGOTIATION=legacy` désactive Tasks.
- `pollIntervalMs` est **borné** par le client entre 250 et 30 000 ms (défaut 2 000 s'il est absent).
- Claude Code n'appelle **ni** `tasks/result` **ni** `tasks/list` : tout passe par `tasks/get`. Un `taskId` doit rester répondable **sur une nouvelle connexion** (une session reprise interroge sur un nouveau canal).
- Une tâche sur serveur **distant** survit à la sortie de Claude Code ; sur serveur **stdio local**, elle meurt avec le processus.
- En HTTP : accepter le job, répondre, **puis** travailler — dans la fenêtre du timer de requête.

> ⚠️ **L'asymétrie qui pose problème** : au 25 octobre, le **SDK TypeScript côté serveur n'implémente pas encore l'extension Tasks** ([typescript-sdk#2189](https://github.com/modelcontextprotocol/typescript-sdk/issues/2189)). Les premiers serveurs Tasks sont donc écrits avec des **méthodes personnalisées** (`tasks/get` codé à la main). C'est un signe de maturité : la spec et le client sont en avance sur le SDK serveur.

### Côté serveurs et outils

- **GitHub MCP Server** : 1.13.0 (02/10) ouvre des outils granulaires *hide/unhide* sur les commentaires d'issue et les reviews, et **retire le flag** `remote_mcp_ui_apps` → MCP Apps UI devient **toujours active**. Puis 2.0.0 (sorties structurées + `outputSchema` gatés sur 2026-07-28) et 2.0.3 (URIs de ressources UTF-8, pagination, gros fichiers).

### Les deux CVE d'audience : pourquoi « mettre à jour » ne suffit pas

· [analyse yaamlabs](https://yaamlabs.com/blog/mcp-sdk-token-audience-cves) · [détail agentbeam](https://agentbeam.com/blog/mcp-python-sdk-three-advisories-1-30-0-2-2-0)

Le défaut est simple à énoncer et difficile à voir : `AuthSettings(token_verifier=...)` côté Python et `requireBearerAuth()` côté TypeScript **vérifiaient la signature et l'expiration**, pas **à qui** le jeton était destiné. Si votre autorisation server émet des jetons pour un CRM *et* pour votre serveur MCP, un jeton légitime du CRM ouvrait votre serveur — et donc vos outils.

> ⚠️ **Le piège rapporté par yaamlabs** : pour le SDK TypeScript, le nouveau contrôle d'audience est **désactivé par défaut** ; il faut un réglage **et** une modification de code. Pour le SDK Python, l'advisory indique qu'aucun changement de code n'est nécessaire, mais **seulement si** votre `TokenVerifier` maison ne faisait pas déjà le travail à moitié. Dans les deux cas : **la montée de version est nécessaire, pas suffisante**. Vérifiez explicitement que `aud` est comparé à **votre** identifiant de ressource.

### Les serveurs de référence : huit correctifs, dont un partiel

Détail de `v2.1.0` (tous les avis sont sur le dépôt `servers`) :

- **`filesystem`** — TOCTOU sur le repli parent (GHSA-53mr-w429-c597) : entre le `realpath` du parent et l'appel système, un processus local remplace le parent par un symlink → **écriture arbitraire hors de `allowedDirectories`**, et via `move_file`, **exfiltration**. Distinct de CVE-2025-53109/53110. **Sur Windows, le correctif n'est que partiel** — l'avis décrit le contournement de configuration.
- **`filesystem`** — chemin vérifié ≠ chemin utilisé (GHSA-7rgq-gccq-qphx) : `/allowed/proj'` passe le contrôle (normalisé en `/allowed/proj`) et l'opération s'exécute sur le **voisin**. Les 14 outils passent par `validatePath` → tous affectés.
- **`filesystem`** — symlink à casse différente accepté sur volume insensible à la casse (régression 2026.8.31) ; `list_directory_with_sizes` révélait taille et mtime d'un fichier hors périmètre.
- **`everything`** — `Access-Control-Allow-Origin: *` : **n'importe quelle page web** visitée par l'utilisateur pouvait appeler `get-env` et lire le résultat (GHSA-mvf5-2qqv-rg3c). Corrigé par un contrôle de l'en-tête `Origin`.
- **`fetch`** — IDNA (vérifie `faß`, se connecte à `xn--fa-hia`) → atteint loopback / metadata cloud, **CVSS 4.0 6.3 mais 7.4 en CVSS 3.1** ; NAT64 jugeait l'adresse IPv6 au lieu de l'IPv4 encapsulée ; `robots.txt` n'était vérifié qu'avant le premier redirect.

> 🧠 **Le fil rouge** : ce sont **tous** des bugs de vérification « sur une représentation différente de celle qui est exécutée ». C'est le motif exact des deux RCE d'IDE du mois. La question à se poser sur chaque garde-fou : *est-ce que j'inspecte exactement la valeur que le noyau/le shell va consommer ?*

### Inspector 2.12.0 : trois CVE dans l'outil qui audite les autres

· [release](https://github.com/modelcontextprotocol/inspector/releases)

- Ouverture d'URL restreinte à `http(s)`, et l'Inspector ouvre **l'URL qu'il a validée** (GHSA-q978-78c7-phqw) : une URL d'autorisation OAuth forgée par un serveur distant ne peut plus exécuter de commande via l'ouvreur de navigateur sous Windows/WSL.
- Validation de l'en-tête `Host` en serveur web de production (GHSA-vcc9-3xgm-p9v4) : ferme la route **DNS rebinding** vers le jeton d'API et les jetons OAuth stockés. Nouvelle variable `MCP_INSPECTOR_ALLOWED_HOSTS` pour les reverse proxies.
- Proxy `/api/fetch` plafonné à **4 MiB** (GHSA-m5pj-3536-3xcp).

Ces trois-là affectent **toutes** les versions v2 de 2.0.0 à 2.11.0. Si vous inspectez des serveurs non fiables avec un Inspector ancien, vous êtes la cible.

### eMudhra : la compromission qui n'a rien à voir avec MCP — mais qui touche tout serveur MCP

· [Talos](https://blog.talosintelligence.com/compromised-intermediate-certificates/) · [Cloudflare](https://blog.cloudflare.com/emudhra-certificate-compromise) · [MSRC](https://www.microsoft.com/en-us/msrc/blog/2026/10/microsoft-response-to-compromised-emudhra-certificate-authority-keys)

Le 19-20 octobre, huit clés privées de CA intermédiaires eMudhra (six TLS, deux signature de code) se révèlent **récupérables depuis les certificats publics** : les clés avaient été générées avec un aléa à un ou deux chiffres au lieu des 384 bits attendus. Un attaquant peut forger un certificat pour **n'importe quel domaine**.

Conséquence pour l'écosystème MCP, qui est le vrai enseignement : `servers v2.2.0` n'est pas une release fonctionnelle, c'est une **release de magasin de confiance**. Les serveurs TypeScript héritent du `certifi`/CA de Node (→ **Node 24.22.1 / 26.12.1+**), `mcp-server-fetch` vérifie via `certifi` (→ **2026.10.23+**), et les serveurs Python sans réseau (`git`, `time`) ne sont pas concernés. Détail piégeux : le champ `engines` accepte **tout** Node 24, donc `npm` **ne vous avertira pas** si vous tournez sur un runtime non patché.

> 🧭 **Ce que ça dit de la maturité** : un serveur MCP est désormais un **service réseau** dont la surface inclut la chaîne de certificats, le runtime et les dépendances transitives. Le périmètre de patch dépasse le dépôt du serveur. C'est la définition même d'un logiciel d'infrastructure.

## Analyse critique

- ✅ **Impactant — à agir**
  - **Auditez l'audience de vos jetons.** `CVE-2026-116684` (Python) et `CVE-2026-111771` (TS) ne se corrigent pas par la seule montée de version si votre `TokenVerifier` maison contourne le contrôle. Comparez `aud` à **votre** identifiant de ressource, explicitement.
  - **`CVE-2026-104850` est la plus grave du lot** malgré son 7.5 : elle ne demande **aucune interaction** et vole des credentials de longue durée (`refresh_token`, `client_secret`). Si vous êtes client MCP avec `authProvider` : `sdk ≥ 1.31.0` / `client ≥ 2.2.0`, **`expectedIssuer` partout**, puis **rotation** des secrets et audit des serveurs connectés.
  - **Traitez `.mcp.json` et tout champ de lancement comme du code exécutable.** L'enseignement combiné de `CVE-2026-103572` et d'opencode : un garde-fou qui compare une chaîne **avant** canonicalisation ne protège rien. Normalisez, puis validez, puis exécutez la valeur normalisée.
  - **Serveurs de référence** : si vous êtes sur une version datée (2025.x / 2026.x), `npm` **ne vous proposera pas** 2.0.1 (le tri sémantique le place en dessous). Installez explicitement.
  - **Runtime et CA** : Node 24.22.1+/26.12.1+, `certifi ≥ 2026.10.23`. Les environnements Python créés avant le 23 octobre gardent l'ancien `certifi`. Recréez-les, ne les mettez pas à jour.

- ⚪ **Anecdotique — pas d'urgence**
  - **Le compteur du registre** : 53 545 serveurs, +42 % en un mois, 67 % de distants. Le chiffre mesure la facilité de publication, pas l'usage. Septembre l'avait déjà établi (62 % mono-version) — octobre n'ajoute qu'un chiffre.
  - **Les téléchargements** : 87 M/semaine npm, 70,8 M/semaine PyPI (×18 face à A2A). Impressionnant, mais gonflé par le CI et les installs automatisées.
  - **Les trois RCE de serveurs d'outils** (`esp-mcp`, `Kali-GPT`, `hagent`) : injection shell par métacaractères, sans version corrigée publiée. Vrais mais niche — à trier selon que vous les exécutez ou non.
  - **Les renommages de gouvernance** (Agents WG → IG, Primitive Grouping → Progressive Disclosure) : de la sémantique, mais qui annonce où vont les budgets.

- 👀 **À surveiller**
  - **SEP-2127 (Server Cards)** : si les hôtes et les registres l'adoptent, la découverte cesse d'être du scraping. S'ils ne l'adoptent pas, on aura un troisième format de métadonnées en plus de la matrice d'extensions et du registre. **Le signal sera le nombre de `.well-known` réellement servis**, pas le merge.
  - **Le SDK serveur TypeScript et Tasks** (`#2189`) : tant qu'il n'implémente pas `io.modelcontextprotocol/tasks`, chaque serveur Tasks est artisanal et divergent. C'est le prochain verrou d'adoption, après celui des Skills.
  - **`requestState` dans MRTR** : jeton opaque transporté par le client, sans réponse publique sur sa protection contre la falsification et la réutilisation. À suivre de près — c'est le point où un attaquant pourrait rejouer une approbation.
  - **Les connecteurs GitHub** : 26 services, annuaire curé, allowlist d'entreprise. Si ce modèle prend, la question « quel serveur MCP installer » devient « quel annuaire mon employeur autorise ». Effet plateforme.
  - **La prochaine révision datée** : `SEP-3398` vient de réécrire le calendrier. La cible communautaire de **2026-12-15** n'a jamais été confirmée par le projet — et c'est ce texte-là qu'il faut lire, pas les billets de blog.

## Conseils / enseignements pratiques

1. **Un seul réflexe de sécurité ce mois-ci** 🔐 : `aud` (audience) et `iss` (émetteur) vérifiés **explicitement**, dans les deux sens (client *et* serveur). Trois CVE sur cinq tournent autour de ça. Ne faites pas confiance à un `provider` par défaut pour le faire à votre place.
2. **Validez la valeur canonique, pas l'entrée brute.** Chemin normalisé (`GetFullPath`, `realpath`, résolution des symlinks), URL dont le schéma **et** l'hôte sont validés, nom d'hôte **identique** entre le contrôle et la connexion (leçon IDNA). Toute asymétrie entre « ce que je vérifie » et « ce que j'exécute » est une faille.
3. **Testez en ère moderne explicite.** Le quickstart TypeScript servait silencieusement l'ère legacy, et l'Inspector en mode `legacy` validait l'erreur. Mettez `--protocol-era 2026-07-28` (ou l'équivalent) dans votre CI, sinon vous testerez le passé.
4. **Traitez les montées majeures de serveurs de référence comme des migrations**, pas des bumps. En v2.0.0, « outil inconnu » devient `-32602` (plus `isError`), les serveurs Python exigent `mcp>=2.3,<3`, et `time` renvoie du `structuredContent`. Trois façons de casser un client en douce.
5. **Pour un serveur long : ne bloquez pas, revenez avec un handle.** Si vous avez des jobs > quelques secondes, Tasks est le bon motif — mais sachez que le support serveur du SDK TS n'existe pas encore et que Claude Code n'appelle que `tasks/get`. Concevez `taskId` comme **durable et résistant au devinage** (il peut faire office de bearer token), et liez-le au propriétaire authentifié.
6. **Bornez ce qui vient du serveur, pas seulement ce qui vient du client.** `CVE-2026-116686` est l'inverse du réflexe habituel : c'est le **client** qui allait chercher une URL choisie par le **serveur** pour valider un `outputSchema`. Résolvez les `$ref` **dans le document**, jamais sur le réseau.
7. **Un `skills/list` vide n'est pas une preuve d'absence.** Un gateway devant un index externe ne peut pas énumérer. Écrivez toujours le chargement d'un skill **par URI seule**, et vérifiez taille **puis** digest (taille d'abord : c'est moins cher et ça échoue plus tôt).

## Mise en perspective

- **MCP a franchi la ligne « protocole → plateforme ».** Le mois ne contient presque aucune nouveauté protocolaire, et pourtant tout a changé : un annuaire curé chez GitHub, des connecteurs OAuth gérés pour l'utilisateur, des UI inline (MCP Apps) dans l'éditeur, des tâches durables dans la CLI. Les briques qui comptent sont désormais **au-dessus** de la spec, dans les hôtes et les annuaires.
- **La distribution est devenue le produit.** 26 services connectables en un clic valent plus, pour l'adoption en entreprise, que n'importe quel SEP. Et c'est un mécanisme de capture classique : le standard gagne techniquement, l'annuaire capte la valeur commerciale. Un éditeur de serveur MCP en 2026 doit se demander *dans combien d'annuaires il figure*, pas seulement *si son serveur est bon*.
- **Le client est redevenu le goulot.** Pendant un an, la spec a couru devant les implémentations. Octobre inverse le rapport : Claude Code implémente Tasks et Elicitation avant que le SDK serveur TypeScript ne sache les produire. La prochaine contrainte d'adoption n'est ni protocolaire ni documentaire — elle est dans la **matrice de support des clients**, et elle bouge par produit, par surface, par version.
- **La surface de sécurité s'est déplacée deux fois.** D'abord du serveur vers le **client** (les deux RCE d'IDE : c'est le client qui lance le processus). Puis du client vers la **chaîne d'approvisionnement** (runtime Node, `certifi`, CA compromise). Un audit MCP qui ne couvre que le code du serveur rate maintenant l'essentiel.
- **Pour un dev** : la bonne nouvelle, c'est que le coût d'entrée continue de baisser (SDKs stables, stateless = déployable n'importe où, exemples corrigés). La mauvaise, c'est que la **surface à opérer** s'élargit plus vite que le protocole ne se stabilise : deux ères à supporter, des extensions à négocier par requête, un magasin de confiance à maintenir, et des clients qui divergent par version. MCP ressemble de moins en moins à un plugin, de plus en plus à une API publique — avec l'obligation de disponibilité, d'observabilité et de gouvernance qui va avec.
