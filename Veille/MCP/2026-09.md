# Veille MCP — Septembre 2026

*Auteur : Nicolas Koudota — 1er octobre 2026*

*Période couverte : septembre 2026 (1 → 31)*

> Le mois de la **consolidation identitaire**. Aucune nouvelle révision datée du protocole n'est sortie — la 2026-07-28 reste la référence — mais septembre a livré trois choses plus structurantes qu'un *date-stamp* : la première extension Final depuis la refonte (*Agent Skills*, SEP-2640), un registre officiel qui a **triplé en quatre mois** (30 375 serveurs), et une ruée sans précédent sur la **couche d'authentification**, déclenchée par une CVE ajoutée au catalogue des vulnérabilités exploitées de la CISA.

---

## 🔥 Les 3 faits marquants

- **Les « Agent Skills » deviennent du protocole** 🧩 : le 13 septembre, SEP-2640 est mergé **Final** sur l'Extension Track — la première proposition acceptée depuis la 2026-07-28. L'extension `io.modelcontextprotocol/skills` ajoute trois méthodes (`skills/list`, `skills/get`, `resources/directory/read`) qui permettent à un serveur de livrer, avec ses outils, **le mode d'emploi de ces outils** : workflow, ordre des opérations, interdits. Design clé : un **digest sha256 + taille par fichier** (pas seulement `SKILL.md`), pour détecter une substitution de fichier après approbation. MCP Inspector avait déjà le support en 2.6.0, quatre jours avant.
- **Le registre officiel triple et se vide de sens** 📈 : 30 375 serveurs uniques (99 114 records de version) au 10 septembre, contre ~9 650 en mai — **×3 en quatre mois**, dont 6 265 nouveaux rien qu'en août. Mais 62 % des serveurs n'ont **qu'une seule version publiée**, 41 % sont restés en 1.0.x/0.x, ~36 % n'ont pas été touchés depuis 3 mois, et les 10 plus gros éditeurs concentrent 17,7 % du catalogue (un seul compte en a publié 1 505, micro-outils générés). Le compte de serveurs est devenu une **métrique de vanité**.
- **La sécurité se déplace vers l'identité** 🔐 : le 2 septembre, `CVE-2026-59822` (bypass d'authentification dans l'endpoint MCP Streamable HTTP de LiteLLM, CVSS 8.8) entre au **KEV de la CISA** avec échéance fédérale au 16. Le 29, Cycode publie `GHSA-qx49-fqc8-xw99` : le **SDK Python officiel** pouvait envoyer son client secret, son code d'autorisation et sa clé PKCE à un endpoint contrôlé par un serveur malveillant. En deux semaines, **cinq mécanismes d'authentification** distincts ont été livrés par cinq éditeurs — sans interopérer. Le trou restant n'est plus l'authentification mais l'**autorisation** (RBAC à l'instanciation, toujours absent du protocole).

## 1. Spécification & gouvernance — la voie des Extensions

### Aucune révision, mais du contenu normatif

Le projet n'a publié **aucune nouvelle révision datée** en septembre. Conséquence directe du framework d'extensions (SEP-2133) : tout ce qui a bougé est passé par là, et le changelog de la prochaine révision reste vide.

- **SEP-2640 — Agent Skills, Final (13/09)** 🧩 · [mcp-news](https://mcp-news.com/news/sep-2640-skills-extension-merged-final) · [spec ext-skills](https://github.com/modelcontextprotocol/ext-skills)
  Identifiant d'extension `io.modelcontextprotocol/skills`. La spec précise explicitement qu'elle ne définit **que le binding de transport** : le format du *payload* appartient à `agentskills.io`. Trois méthodes, aucun nouveau transport, aucun nouveau format :

```json
// 1) Énumérer les skills servis par un serveur
{ "method": "skills/list", "params": {} }

// 2) Résultat : frontmatter verbatim + manifeste de CHAQUE fichier
{
  "uri": "skill://git-workflow/SKILL.md",
  "resources": [
    { "uri": "skill://git-workflow/SKILL.md",
      "digest": "sha256:b95a384300adeea2d902f7d19cd7c04b378ef58e09759107b9c7db4dcacbaa25",
      "size": 1428 }
  ]
}
// 3) skills/get (un skill par URI) + resources/directory/read (optionnel)
//    Les fichiers sont des ressources ordinaires → lus par resources/read
```

> ✅ **Pourquoi le digest par fichier compte** : un premier brouillon ne digérait que `SKILL.md`. Un serveur pouvait donc faire approuver un skill anodin, puis **échanger un fichier de référence** que le modèle lit tout aussi fidèlement. Désormais tout fichier ajouté/modifié = échec de vérification, et une lecture dont la taille diffère du manifeste échoue **avant même** le calcul du digest.

- **Adoption réelle du Skills : 2 sur 572** 👀 · [dev.to, 24/09](https://dev.to/piekwerk/skills-over-mcp-is-final-what-3-methods-and-per-file-digests-change-for-your-agents-25jk)
  Kin Lane a sondé 1 432 endpoints MCP hébergés : 572 ont complété le handshake, **exactement deux** déclarent l'extension (Hugging Face et une place de marché française du bâtiment, RenooLab). Contrepoint intéressant : parmi les 679 fournisseurs d'API de son catalogue qui publient déjà des skills maison (2 568 skills), **270 opèrent déjà les deux moitiés** — le serveur MCP et les instructions — dans deux endroits séparés. Côté SDK : les PR sont ouvertes sur Go (passe la suite de conformité), TypeScript, Python et C# ; mais le vrai verrou est **l'adoption côté hôtes**.

### DPoP et identité agent : le chantier central

La roadmap « agent identity » se matérialise enfin en code côté SDK TypeScript (**2.1.0**, 21-23/09) : support **DPoP (RFC 9449 / SEP-1932)**, les jetons d'accès étant liés à une clé détenue par le client — un jeton volé devient inexploitable tel quel.

```ts
// Opt-in côté client : implémenter le hook dpop() du provider OAuth
const provider: OAuthClientProvider = {
  // ...
  dpop: () => session,          // retourne un DpopSession
};
// Helpers : generateDpopKeyPair(), accessTokenHash(), isDpopNonceChallenge()
// Flux auth() / exchangeAuthorization / refreshAuthorization / fetchToken signent
// désormais une preuve DPoP, avec 1 retry sur challenge `use_dpop_nonce`.
```

En parallèle, `@modelcontextprotocol/server@2.1.0` introduit le **scope challenge au moment de la requête** : `requireScopes` + `createMcpHandler` renvoient **HTTP 403 + `insufficient_scope`** *avant* l'exécution du handler ou l'ouverture d'un flux SSE. Le serveur cesse de laisser fuiter le comportement d'un outil sous-scopé, et le client sait quel scope demander.

- **CNCF — MCP candidat au rang de *wire spec* cloud-native** 🏛️ · [Forkast, 21/09](https://forkast.news/cncf-evaluates-mcp-as-the-cloud-native-agent-wire-spec-and-the-standardization-arc-just-reached-infrastructure/)
  L'initiative **TOC #1746** (« Cloud-Native Foundations for Distributed Agentic Systems ») évalue MCP comme spécification filaire par défaut pour les systèmes d'agents distribués sur Kubernetes — trois *streams* (interopérabilité, **gateway agentique**, abstraction runtime), deux livrables en phase de proposition (*MCP-for-Clusters*, **Agent CRD**). `kagent` (CNCF Sandbox, Solo.io) implémente déjà un `MCPServer` en CRD. C'est une **évaluation, pas un standard ratifié** — mais l'arc de standardisation (Anthropic → AAIF/Linux Foundation → CNCF) place MCP au niveau le plus bas de la pile.

### AGNTCon + MCPCon Europe — la première conférence dédiée

Du 16 au 18 septembre à Amsterdam, sous l'égide de l'**Agentic AI Foundation** (fondée en décembre 2025 par Anthropic, OpenAI, Google et d'autres sous le Linux Foundation), s'est tenue la première conférence du protocole. · [heise, 17/09](https://www.heise.de/en/news/AGNTCon-MCPCon-Agentic-AI-Matures-11456812.html)

- Keynote de **David Soria Parra** (co-inventeur de MCP, Anthropic) : les modèles Claude ont exécuté **plus d'un milliard d'appels d'outils MCP**.
- Thème dominant : la **professionnalisation** — les serveurs MCP ne sont plus des bouts de code sur le laptop d'un expérimentateur, mais des services réseau soumis aux mêmes exigences de sécurité, d'observabilité et de scalabilité.
- La refonte stateless de juillet (suppression du handshake, remplacement du canal retour permanent par **MRTR**) a été **critiquée** comme trop fréquente — d'où la promesse d'une **dépréciation formelle avec 12 mois minimum** avant toute suppression.

## 2. Implémentations — SDKs & serveurs

### Le fil rouge du mois : borner les lectures non bornées

**Cinq SDK officiels** ont corrigé en un mois un défaut de transport HTTP non borné (Kotlin, Python, Go, et les lignes legacy). La formulation de `mcp-news` est juste : un serveur MCP est un **service réseau ordinaire avec un appelant extraordinaire**, et il attrape des bugs web ordinaires. Détail des bornages livrés :

| SDK | Ce qui est désormais borné |
|---|---|
| **Go 1.8.0** | Profondeur d'imbrication JSON · taille d'événement SSE · longueur de frame stdio · réponses d'enregistrement client OAuth dynamique |
| **Python 2.2.0 / 1.30.0** | Redirect HTTP **same-origin only** · sessions idle fermées à 30 min · `max_sessions` 10 000 (503 au-delà) |
| **TypeScript 2.1.0 / 2.2.0 / 1.30.1** | Body **4 MiB** sur tous les chemins SDK (413 `RequestBodyTooLargeError`) · longueur des batches JSON-RPC |
| **Kotlin 0.14.0** | Chunked-encoding sans `Content-Length` (contournait le pré-contrôle) · SSE serveur sans terminateur (heap client) |
| **Rust rmcp** | Backoff de reconnexion SSE saturé (évite le panic par overflow) |

### Écosystème client : quand le « préférer le plus récent » casse

**Goose 1.50.1** mérite d'être cité comme cas d'école 👀 · [mcp-news](https://mcp-news.com/news/goose-1-50-0-ships-then-1-50-1-reverts-latest-mcp-version-preference)

- **1.49.0** (03/09) : sampling pour réponses *reasoning-first*, clients OAuth pré-enregistrés, tests de conformité MCP en CI, sanitization des tags Unicode dans les prompts.
- **1.50.0** (08/09) : « Prefer latest MCP version » — tentative de 2026-07-28 via `server/discover` avant fallback legacy.
- **Régression immédiate** : les extensions *stdio* dont le serveur ne parle que jusqu'à 2025-11-25 **ne démarraient plus** ; celles en *streamable_http* contre un serveur qui garde son canal de notification ouvert mais silencieux échouaient en `empty sse stream`.
- **1.50.1** (14/09) : revert pur. **Leçon** : la négociation ascendante doit rester **tolérante aux serveurs legacy bavards ou silencieux**, pas seulement « tenter le plus récent d'abord ».

**github-mcp-server 1.12.1** (08/09) corrige un bug d'OAuth intéressant : la metadata *protected-resource* annonçait **tout le catalogue de scopes** du serveur au lieu des seuls scopes par défaut — et les clients comme VS Code lisaient ça comme la *demande d'autorisation initiale*. `delete_repo` et `workflow` restent atteignables, mais uniquement via les *challenges* d'autorisation par outil. C'est exactement le pattern **moindre privilège en deux temps** promu par la roadmap.

**Playwright MCP 0.0.81** 👀 : la vérification d'accès fichier **suit maintenant les symlinks** — un lien symbolique dans le workspace ne peut plus lire/écrire hors des racines autorisées. Livré en *release note*, **sans advisory de sécurité**. Le même pattern (comparaison de chemins sans résolution de liens) était déjà apparu sur Chrome DevTools MCP en août.

## 4. Retours d'expérience & bonnes pratiques

### Le Skills : la spec est finie, le service manque

Le constat le plus utile du mois vient de l'écart mesuré (cf. §1) : **2 endpoints sur 572** déclarent `io.modelcontextprotocol/skills`. L'auteur du décryptage (dev.to, 24/09) formule la bonne règle de lecture : *« la spec est Final depuis neuf jours. Le design est fait ; c'est le service qui manque. »* Pour un développeur de client, deux pièges sont explicitement documentés par la spec :

1. **Un résultat `skills/list` peut être vide ou partiel légitimement** — un serveur de doc transformant chaque endpoint en skill peut en avoir des milliers, un *gateway* devant un index externe ne peut pas énumérer du tout. La spec interdit de traiter un listing vide comme preuve d'absence de skills, et impose de savoir charger un skill **par sa seule URI**.
2. **Les SDK ne sont pas prêts** — PR ouvertes, Go seul passe la conformité. Le signal à suivre n'est pas le dépôt de spec mais la **matrice des clients**.

### Bindings legacy vs modernes : la compat n'est pas un détail

Le mois a répété le même enseignement, trois fois (Goose, github-mcp-server, Playwright MCP) : dans un monde **dual-era** (modernes ≥ 2026-07-28, legacy ≤ 2025-11-25, *dual-era* pour les deux), le chemin critique est toujours le **repli**. Deux détails de terrain qui reviennent :

- `Mcp-Method` et `Mcp-Name` sont **obligatoires** sur chaque POST Streamable HTTP, et le serveur doit rejeter tout écart en-tête/corps avec **`-32020`**. Le code d'erreur des paramètres invalides a aussi bougé de `-32002` à `-32602`.
- `ping`, `logging/setLevel`, `resources/subscribe`, le flux GET autonome et la reprise par `Last-Event-ID` ne sont **pas dépréciés : ils sont supprimés**. Une réponse coupée = requête perdue, à réémettre avec un nouvel id.

### Le vrai coût : le contexte, pas le transport

Signal secondaire mais récurrent dans les analyses du mois : la charge de description. Trois serveurs MCP dans une session peuvent consommer **143 000 tokens sur 200 000** disponibles (72 %) ; le serveur GitHub officiel annonçait ~42 000 tokens avant tout travail, un décompte plus récent 55 000 sur 93 définitions d'outils (~21 % d'une fenêtre 200 K). C'est exactement ce que la roadmap adresse sous « improved primitives » via une **découverte progressive** : un petit point d'entrée qui révèle le catalogue à mesure que la conversation se resserre.

## 5. 🔒 Sécurité & gouvernance — le mois de l'identité

### La bascule : une CVE dans le KEV change la trajectoire

**`CVE-2026-59822` — LiteLLM MCP Streamable HTTP** (CVSS 8.8) est l'événement déclencheur. Ajoutée au **catalogue KEV de la CISA le 2 septembre** avec échéance fédérale au **16**, elle permettait à **n'importe quel bearer token fabriqué** d'obtenir une session MCP authentifiée : la cause racine est un fallback OAuth2 passthrough qui substituait un objet `auth` vide au lieu de rejeter une validation de clé échouée. · [CISA KEV](https://www.cisa.gov/known-exploited-vulnerabilities-catalog) · [analyse WorkOS](https://workos.com/blog/mcp-authorization-failures)

**`GHSA-qx49-fqc8-xw99` — SDK Python officiel** (29/09, Cycode) · [advisory](https://github.com/modelcontextprotocol/python-sdk/security/advisories/GHSA-qx49-fqc8-xw99) · [The Hacker News](https://thehackernews.com/2026/09/official-mcp-python-sdk-flaw-can-let.html)
Un serveur MCP malveillant pouvait convaincre le SDK d'envoyer **client secret + code d'autorisation + clé de preuve PKCE** vers un endpoint de jeton contrôlé par l'attaquant. Cause : un **chemin de repli legacy dans la découverte OAuth** qui sautait la validation de l'issuer quand le chemin principal renvoyait un 404.
> ⚠️ **Le piège à retenir** : corriger la version ne suffit pas. Qui utilise `ClientCredentialsOAuthProvider` ou `PrivateKeyJWTOAuthProvider` doit **en plus passer explicitement `issuer=`** — sinon la vulnérabilité persiste. Corrigé en 1.30.0 et 2.2.0.

**`GHSA-84m7-p3x7-pcfv` — SDK Python, sessions jamais récupérées** (30/09) · [advisory](https://github.com/modelcontextprotocol/python-sdk/security/advisories/GHSA-84m7-p3x7-pcfv)
En mode *stateful* (le défaut), l'état de session n'était **jamais reclamé** et l'`initialize` d'origine était **conservé**. Affecte 1.8.0→1.29.1 et 2.0.0→2.1.1. C'est exactement ce que `session_idle_timeout` (30 min) et `max_sessions` (10 000) viennent borner en 2.2.0 / 1.30.0.

### 🦠 Deadbugz — la campagne supply-chain du mois

La ressource sécurité la plus importante de septembre n'est pas une CVE mais une **campagne active** · [Adversa, 07/09](https://adversa.ai/blog/top-mcp-security-resources-september-2026/) · [Pillar Security](https://www.pillar.security/blog/deadbugz-currently-active-mcp-supply-chain-campaign)

- Un compte unique a déposé **23 pull requests sur des projets IA et dev sans rapport, en 74 minutes**.
- Le serveur MCP offert propose **deux outils anodins** (formatage de texte, résumé).
- **Après exactement trois appels d'outils**, il **réécrit ses propres métadonnées** en instructions de chasse aux clés SSH, credentials AWS, historique shell et config Kubernetes — **en dissimulant l'activité à l'utilisateur**.
- Les IOC sont publiés (endpoint, chemin de l'artefact local, dépôt).

> ⚠️ **La conclusion qui change la pratique** : Deadbugz rend la **revue unique structurellement insuffisante**. Un serveur qui se comporte bien pendant trois appels puis modifie ses descriptions d'outils passe *tous* les contrôles d'avant-approbation. Il faut donc **surveiller la dérive des métadonnées *après* approbation** : si le client met les définitions d'outils en cache, les comparer à chaque reconnexion et **alerter sur le diff**.

### Les cinq mécanismes d'authentification, en deux semaines 🧱

· [Forkast, 30/09](https://forkast.news/five-mcp-authentication-mechanisms-shipped-in-two-weeks-the-pattern/)

- **Okta Agent SSO** (GA 24 août) — protocole *Cross App Access*, l'extension officielle **Enterprise-Managed Authorization** : les agents deviennent des identités de première classe, sans prompt de consentement à l'exécution.
- **SSOJet MCP Authentication** (beta, sept.) — pont B2B SSO : protéger un serveur MCP avec l'IdP **du client** (Okta, Entra ID, Google Workspace, OneLogin). Argument : quelques jours vs 6-12 semaines.
- **Rubrik MCP** (GA 30 sept.) — MCP dans la surface *backup/resilience*.
- **GitHub Copilot MCP customizer** — secrets préfixés `COPILOT_MCP_`, PAT, OAuth distant, gateways SSO entreprise, tout via les réglages du dépôt.
- **Operant AI MCP Gateway** — autorisation *runtime intent-aware* sur chaque invocation, audit corrélé au contexte d'identité Okta.

> ⚠️ **Aucun de ces cinq mécanismes n'interopère.** Et aucun ne comble le trou de fond relevé par la NSA dans une *Cybersecurity Information Sheet* de mai 2026 : **MCP ne sait pas échanger de permissions RBAC à l'instanciation**. L'authentification répond à *qui se connecte* ; l'autorisation — *ce que cette connexion a le droit de faire* — reste une décision propriétaire. Les cinq mécanismes traitent la couche identité ; la couche permissions est ouverte.

> 🧭 **Pattern global** : le protocole a été publié en novembre 2024 **sans framework d'authentification obligatoire**. L'auth est arrivée plus d'un an plus tard, quand des milliers de serveurs étaient déjà déployés sans. La gouvernance arrive **après** la fenêtre de brèche, pas avant.

## Analyse critique

- ✅ **Impactant — à agir**
  - **Mettre à jour le SDK Python en 2.2.0 / 1.30.0 et passer `issuer=` explicitement** sur `ClientCredentialsOAuthProvider` / `PrivateKeyJWTOAuthProvider`. C'est la seule action de sécurité de septembre réellement non négociable : la version seule ne corrige pas (GHSA-qx49).
  - **Traiter l'allowlist OAuth comme le contrat initial, pas le catalogue complet** (github-mcp-server 1.12.1). Si votre serveur annonce *tous* ses scopes dans la metadata *protected-resource*, vos clients demandent tout. Laissez les scopes sensibles derrière les *challenges* par outil.
  - **Brancher une surveillance de dérive des métadonnées d'outils** après approbation. Deadbugz ne se détecte pas avant l'installation ; il se détecte au **diff** des descriptions d'outils à la reconnexion.
  - **Borner les lecteurs HTTP** : body limit, profondeur JSON, taille d'événement SSE, longueur de frame stdio, redirects same-origin, expiration de session. Cinq SDK officiels ont eu ce défaut le même mois — votre serveur maison l'a probablement aussi.
  - **Évaluer DPoP** (RFC 9449 / SEP-1932) si vous opérez un serveur MCP distant ou un gateway : le SDK TS client supporte désormais, c'est purement *opt-in*, aucun impact sur l'existant.

- ⚪ **Anecdotique — pas d'urgence**
  - Le **compte de serveurs** du registre : 30 375, ×3 depuis mai… mais 62 % mono-version, un éditeur avec 1 505 micro-outils. Métrique de vanité, à ne pas mettre dans un *slide* de décision.
  - Les **renommages d'outils** de gouvernance Microsoft (Partner Center) : l'ancien chemin reste ouvert jusqu'à fin octobre, les serveurs déjà certifiés ne resoumettent pas.
  - **Casdoor / MCPHub / SiYuan / PraisonAI** : correctifs publiés **avant** les records CVE, souvent de plusieurs semaines. À trier selon votre surface réelle, pas selon le score CVSS brut.
  - Les 33 records sécu du 3-15 septembre : beaucoup sur des serveurs de niche mono-usage.

- 👀 **À surveiller**
  - **L'écart spec ↔ terrain du Skills.** 2 endpoints sur 572 déclarent l'extension. Si la matrice des clients ne bouge pas d'ici la prochaine révision, SEP-2640 restera un beau texte. **Le signal est la matrice clients, pas le dépôt de spec.**
  - **CNCF TOC #1746** — si l'initiative produit un standard ratifié, la question passe de « quel cloud a des agents » à **quel wire spec ils parlent tous**. `kagent` en Sandbox est le précurseur concret.
  - **RBAC à l'instanciation** (constat NSA) : cinq vendors ont traité l'identité, personne n'a traité les permissions. C'est le prochain front.
  - **La prochaine révision (cible 2026-12-15)** : cible du seul Transports WG, non confirmée par le projet. Rien n'est déprécié depuis le 28 juillet ne peut être retiré avant une révision publiée **à partir du 28 juillet 2027** — la fenêtre est confortable, mais **HTTP+SSE a l'exit le plus court du lot** (3 mois après que SEP-2596 est devenu Final), pas le plus long : c'est le registre normatif qui fait foi, pas le billet de blog.
  - **Coût en contexte** : 55 000 tokens avant le premier prompt sur le serveur GitHub officiel. La découverte progressive annoncée en roadmap est le chantier à surveiller côté usage réel.

## Conseils / enseignements pratiques

1. **Faites la chasse au « non borné »** 🧱 : `Content-Length` max, profondeur JSON, taille d'événement SSE, longueur de frame stdio, nombre de sessions, TTL de session idle, redirects restreints à l'origine. C'est le défaut n°1 de tout l'écosystème en 2026 — et il ne dépend pas du protocole, juste de votre code de transport.
2. **Passez le `issuer` explicitement** partout où vous utilisez un provider d'identités machine-à-machine côté SDK Python. Traitez la mise à jour de version comme nécessaire **mais non suffisante**.
3. **Déclarez peu de scopes par défaut**, et le reste derrière des *challenges* par outil. Un agent demande l'union de tout ce que vous annoncez — c'est le premier poste d'élargissement involontaire de privilèges.
4. **Surveillez les métadonnées d'outils après approbation**, pas seulement avant. Le modèle de menace a changé de temporalité : la revue ponctuelle ne suffit plus contre un serveur qui retourne sa veste au 4ᵉ appel.
5. **Traitez un `skills/list` vide comme non concluant** si vous écrivez un client : un gateway devant un index externe ne peut pas énumérer. Supportez toujours le chargement d'un skill **par URI seule**.
6. **Testez le repli, pas seulement le chemin moderne.** La régression Goose (1.50.0 → 1.50.1, six jours) montre que « préférer le plus récent » casse sur les serveurs legacy silencieux ou bavards. En CI : tester les deux chemins, plus un serveur qui garde un canal ouvert sans rien envoyer.
7. **Ne confondez pas authentification et autorisation.** Un serveur MCP exposé doit avoir *la validation du jeton* **et** une décision de rôle sur ce que l'agent peut atteindre. Le walkthrough Oracle/Keycloak (rôle → pool de base de données, pool → privilège SQL) est un template directement transposable.

## Mise en perspective

- **Un protocole, deux couches qui se séparent.** Le passage stateless d'août a réglé la question du transport. Septembre a montré que la valeur — et le conflit — se déplacent vers **la découverte** (registres, marketplaces, Server Cards, kagent CRD) et **l'identité** (DPoP, ID-JAG, enterprise-managed auth, gateways). Le protocole proprement dit se banalise ; ce sont ses annexes qui deviennent stratégiques.
- **L'interopérabilité s'améliore, la sécurité reste morcelée.** Cinq mécanismes d'authentification non interopérables en deux semaines, chacun couvrant sa couche, aucun traitant les permissions. C'est un progrès réel *et* une fragmentation. La prochaine phase se jouera sur la convergence ou sur la constitution de silos propriétaires qui fragmentent l'écosystème d'agents.
- **Gouverner après le déploiement.** La chronologie est constante : protocole (nov. 2024) → milliers de serveurs déployés → authentification (>1 an plus tard) → gouvernance d'identité (sept. 2026). Les taux d'exposition (38-40 % sans auth, 91,8 % dans l'échantillon arXiv) sont la facture de cet ordre-là. Le corollaire pratique : **votre revue de surface d'attaque MCP vaut plus que votre veille de version**.
- **L'effet plateforme s'installe par le catalogue.** Claude Marketplace (2 000 outils), Partner Center, registre officiel, GitHub MCP, kagent : la bataille n'est plus le protocole mais **qui possède l'index** et dicte les conditions d'entrée (scan de sécurité, revue humaine, manifeste, Key Vault). C'est le schéma classique du standard qui gagne techniquement et se fait capturer commercialement à la couche d'annuaire.
- **Pour un dev** : le coût d'entrée baisse (SDKs stables, spec claire, stateless = serverless), mais le **coût de la fiabilité** monte — borner, authentifier, autoriser, surveiller la dérive, gérer le dual-era. MCP ressemble de plus en plus à une API publique à opérer, et de moins en moins à un plugin à brancher.
